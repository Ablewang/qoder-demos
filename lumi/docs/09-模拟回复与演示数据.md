## 1. 演示边界与来源约定

- 城市固定杭州，前端每次聊天 city="杭州"；路线起点固定武林广场。没有真实定位／定位权限请求或城市切换表单。

## 2. 意图、历史与范围限制

### 2.1 请求与返回

来源：Types／ChatRequest、Message、Intent、AgentCard；UseChat／send；Data／MockReply、createMockReply。

| 请求字段 | 含义 |
| --- | --- |
| conversationId | 本地会话ID |
| query | 当前用户问题或按钮query |
| city | 前端固定杭州；制天气／forecast时trim，空值回退杭州 |
| history | 可选，仅role=user／assistant、content字符串。新问题取此前done消息；重试取目标助手对应用户问题之前的done消息，不含目标问题、旧回复或后续，最多最后12条 |

MockReply全部字段：`intent`、`text`、`cards`、`suggestions`、`thinking`、`plan`。baseReply返回前四项；createMockReply再调用process按首张卡片附过程。每个当前分支cards为零或一张；无卡时thinking=""、plan=[]。

卡片共十一种。新增场景**不是三个新增Intent字面量**：forecast仍属于weather_outfit，itinerary对应新增day_plan，checklist对应新增checklist。Types／Intent共有weather_outfit、food_recommend、recipe、hotel_recommend、route_plan、nearby_search、reminder、home_care、day_plan、checklist、chitchat。

### 2.2 explicitIntent精确优先级

来源：Intent／explicitIntent。按下表从上到下，第一个命中返回；不是语义理解或约束搜索承诺。为避免中文概述遗漏，记录实际regex（表内`\|`仅为Markdown转义，正则中为普通`|`）。

| 顺序 | Intent | 实际regex／前置条件 |
| --- | --- | --- |
| 1 | reminder | `/提醒\|备忘\|闹钟\|记得\|别忘/` |
| 2 | checklist | **不含**`/我的清单/`且命中`/带什么\|带哪些\|要带\|打包\|行李\|准备什么\|准备哪些\|列个清单\|出行清单\|购物清单\|买菜清单\|采购/` |
| 3 | day_plan | `/一日游\|半日游\|玩一天\|逛一天\|行程\|周末去哪\|怎么玩\|(?:一天\|半天\|周末\|周六\|周日).*(?:怎么逛\|去哪)/` |
| 4 | route_plan | `/怎么走\|如何(?:去\|到)\|路线\|导航\|交通\|地铁\|公交\|打车\|步行\|骑行\|开车\|换一种方式/` |
| 5 | recipe | `/菜谱\|食谱\|详细步骤\|烹饪\|做法\|怎么做\|如何做\|炒蛋\|炖汤\|简单菜/` |
| 6 | weather_outfit | `/天气\|气温\|温度\|下雨\|下雪\|穿什么\|穿搭\|穿衣\|搭配\|冷不冷\|热不热/` |
| 7 | hotel_recommend | `/酒店\|民宿\|住宿\|住哪\|住一晚\|住两晚\|住几晚\|小住\|订房/` |
| 8 | nearby_search | `/附近.*咖啡\|咖啡.*附近/` |
| 9 | food_recommend | `/吃什么\|吃点\|吃饭\|餐厅\|美食\|午餐\|晚餐\|早餐\|午饭\|晚饭\|早饭\|好吃\|咖啡\|清淡\|推荐.*吃/` |
| 10 | home_care | `/家务\|收纳\|打扫\|清洁\|洗衣\|晾晒\|养护\|绿植\|居家\|整理房间/` |
| 11 | route_plan | `/(?:去\|到\|前往).*(?:西湖\|杭州东站\|灵隐寺)/` |
| 12 | nearby_search | `/附近\|周边\|便利店\|药店\|公园\|书店/` |
| 13 | chitchat | 以上未命中 |

例：“提醒我出门带什么”先reminder；“出行清单里有交通卡”先checklist，不被交通抢走；“周末去哪玩，怎么走”先day_plan；“推荐步行可达的餐厅”仍先route_plan。“我的清单”只抑制第2项，不等于实现打开清单的导航意图，也不阻止后面其他词命中。“咖啡”单词进入food_recommend，有“附近”咖啡进入nearby_search。

**forecast二级分支regex：**已经进入weather_outfit后，当前query命中`/周末|这周|本周|未来|几天|三天|五天|一周|下周/`且**不命中**`/今天|明天/`，才makeForecast；否则当日weather。因此“这周天气怎么样”给五日卡，“今天到下周天气”仍weather；“周末去哪玩”先day_plan，不是天气。

### 2.3 短追问继承

来源：Intent／detectIntent；Data／contextQuery。

当前完整短语识别：`/^(?:请|帮我)?\s*(?:换一家|换一间|换一个|清淡一点|详细步骤|换一种方式|再详细一点|展开说说)[！!。？?\s]*$/`，先trim。不是所有含这些字的长句都继承。

1. 意图先倒序查user历史，再倒序查assistant；跳过符合`/^(?:换一家|换一间|换一个|清淡一点|详细步骤|换一种方式)[！!。？?\s]*$/`的历史，首个非chitchat意图返回。
2. 无历史可继承：“详细步骤”回退recipe，“换一种方式”回退route_plan，“清淡”或“换一家”回退food_recommend，其余按当前query。
3. contextQuery仅对同一组当前短追问，找上一条user且不符合上述较窄跳过regex，拼为`{previous.content或空} {request.query}`；不查assistant正文。
4. 历史跳过不含“再详细一点／展开说说”、不跳过带请／帮我的历史短语；不能描述成可靠无限记忆。
5. 餐厅清淡／换一家只看当前query；附近咖啡、路线目的地、checklist买菜选择可看combined。forecast二级条件只看当前query，不继承“这周”时段。因此预报后短问不保证仍给五日卡。

### 2.4 城市与路线范围拦截

来源：Data／baseReply、makeRoute。

当前query含`/北京|上海|深圳|广州|成都|重庆|南京|苏州|宁波|东京|纽约|巴黎/`，且intent属于weather_outfit（**含forecast**）、food_recommend、hotel_recommend、nearby_search、route_plan、**day_plan（itinerary）**时，先返回杭州限制、无卡。只查当前query，非完整城市实体识别、不查combined。recipe、reminder、home_care、**checklist**、chitchat不经过该拦截；例如北京出行物品清单仍可能给固定packing示例，不能据此承诺异地数据。

route_plan的当前query用`/从(.+?)(?:到|去)/`抽起点，片段不含武林广场则返回起点限制。无该形式不等于识别了任意起点，只是默认武林广场。目的地当前query优先，再combined，按西湖→杭州东站／火车东站→灵隐寺的数组优先；多个地点不变成多站路线。itinerary是独立固定四站示例，不是makeRoute的自由多点规划。

## 3. 全部回复正文与追问

来源统一为Data／baseReply对应case；thinking／plan见第12.1节。引用块为正文原文；动态模板覆盖城市、日期和顺序变体。suggestions既为按钮文字也为query，仅最后一条done助手在无statusText时显示，busy禁用。

### 3.1 其他城市限制

> 目前仅提供杭州的生活演示，不会把其他城市的问题套用到杭州。你可以看看杭州示例，真实信息请在地图或天气应用中确认。

cards=[]，intent保留检测值。suggestions：今天杭州穿什么；推荐杭州午餐；从武林广场去西湖怎么走。

### 3.2 天气与穿搭

通常城市杭州、当前query不含明天：

> 今天可以考虑轻薄上衣配长裤，再带一件方便穿脱的外套。杭州早晚偏凉，舒适的鞋也很重要。下面是演示天气，出门前请确认实时预报。

含明天时仅首词变“明天”；完整模板：`{今天或明天}可以考虑轻薄上衣配长裤，再带一件方便穿脱的外套。{city}早晚偏凉，舒适的鞋也很重要。下面是演示天气，出门前请确认实时预报。`

intent=weather_outfit，cards=[weather]；suggestions：适合去哪里散步；推荐一顿清淡午餐；提醒我带伞。明天只切正文，不更新天气数字、小时或衣物。

### 3.3 五日预报（forecast）

条件为第2.2节天气二级分支；intent仍weather_outfit。

> 未来五天{city}整体偏凉，{rainy.label}有小雨，记得带伞；其余几天适合出门走走。下面是演示预报，出门前请确认实时天气。

cards=[forecast]；suggestions：`提醒我{rainy.label}早上八点带伞`；周末去哪玩；出门要带什么。rainy取最高rain，当前固定第四天70%。label按北京时间今天星期偏移计算，不固定某个周几；完整日期规则与固定值见第4.3节。

卡片行动按钮只有最高rain≥50才显示；本分支正文与suggestions直接选最高rain，不另做阈值检查（固定数据达阈值）。不查询未来实时天气、不自动创建提醒。

### 3.4 餐厅

不含清淡／少油／素食：

> 这一餐，给你三种选择：家常菜、蔬食和热汤面。一人吃或赶时间，就选一碗热汤面。门店与价格均为示例，出发前记得核对地址。

含上述词：

> 这一餐，给你三种选择：家常菜、蔬食和热汤面。清淡的选择放在前面，可以备注少盐、酱汁另放。门店与价格均为示例，出发前记得核对地址。

当前query含“换一家”时，在口味建议之后、门店限制之前加：`当前只有这三家演示餐厅，本次仅调整顺序，没有查询新门店。`，清淡与换一家同时出现也加。

intent=food_recommend；cards=[restaurants]：默认title“把这一餐吃得舒服”，清淡“清淡一点，也好好吃饭”。默认新白鹿→清禾→巷口；清淡清禾→巷口→新白鹿；非清淡且换一家巷口→新白鹿→清禾。suggestions：清淡一点；番茄炒蛋怎么做；去西湖怎么走。只重排三样例，不查询饮食约束或新餐厅。

## 11. 提醒字段与时间解析

来源：Data／makeReminder、chineseNumber、chinaDate、baseReply的reminder；Types／ReminderCard。只描述有限一次性解析，非真实调度。

### 11.1 全部字段与入口

| 字段 | 值／规则 |
| --- | --- |
| type | reminder |
| id | `reminder-{timestamp}-{encodeURIComponent(清理后的title)}`，清理为空时编码仍空，不编码显示兜底“待办提醒” |
| title | 按第11.5节清理当前query；空则待办提醒 |
| dueAt | timestamp转UTC ISO字符串 |
| note正常 | 时间按杭州（北京时间）解析。仅生成提醒建议，确认保存后仍需自行设置系统通知。 |
| note顺延 | 所选时间已过，已顺延至次日。时间按杭州（北京时间）解析。仅生成提醒建议，确认保存后仍需自行设置系统通知。 |

入口必须reminder意图，先重复词限制、再`/(?:点|时|\d:\d|分钟后)/`，才makeReminder。小时后／半小时后含“时”可过；明天晚上取快递／明天浇花缺时刻继续追问。入口不是完整时间校验，无通用无效输入澄清。note说自行设置系统通知，不代表有系统通知按钮。

### 11.2 日期基准

local=now+8小时，midnight=该local UTC年月日零点-8小时。后天优先偏移+2、明天+1，其他0。星期regex=`/(?:下周|周|星期)([一二三四五六日天])/`：周一～周日／周天、星期一～日／天取从今天未来0～6天对应日，今天同星期则0；下周以周一开始，取下一自然周对应日，并覆盖明天／后天偏移。

只支持中文星期；不正式解析YYYY-MM-DD、月日、节假日、下个月、每隔几天等。未支持日期词可能按默认或已识别相对日期算，不一定拒绝，不能承诺任意绝对日期提醒。

### 11.3 时刻与中文数字

- 数字纯阿拉伯整数Number；单字零、一、二、两、三、四、五、六、七、八、九。含十按十位个位拆，例如十／十一／二十／二十三，不是百千数词解析。
- clock实际regex：`/([零一二两三四五六七八九十\d]{1,3})(?:点|时)(?:(半|一刻|三刻)|([零一二两三四五六七八九十\d]{1,3})分?)?|([01]?\d|2[0-3]):([0-5]\d)/`。
- 点／时后可半=30、一刻=15、三刻=45或分钟数；未给分钟0；冒号分钟两位00～59。
- 无clock：晚上／今晚默认19点，否则下午15点，其余9点，仍受入口检查约束。
- 下午／晚上／今晚／傍晚且hour<12加12；凌晨／午夜且hour=12改0；hour限制0～23，minute上限59，不因越界给专门澄清。
- 早上／上午／中午无独立小时偏移；不是完整健壮的自然语言时间服务。

### 11.4 相对时间与顺延

relative=`/([零一二两三四五六七八九十\d]+)\s*(分钟|小时)后/`；从now加max(1,chineseNumber)对应分钟／小时，覆盖前面日期时刻计算。`/半(?:个)?小时后/`再覆盖为now+30分钟。若timestamp≤now仅加1天并加顺延note；不是重复提醒，也不会启动定时器。

### 11.5 title清理原样

1. 前缀regex=`/^(?:请|帮我|请帮我)?(?:设置)?提醒(?:我)?/`，去提醒／提醒我／设置提醒等；备忘／闹钟／记得／别忘不在清理前缀，可保留标题。
2. 全局去今天／明天／后天／今晚、下周／周／星期+中文星期、早上／上午／中午／下午／晚上／傍晚／凌晨／午夜。
3. 全局去可识别点时表达、冒号时刻和数字分钟／小时后，再trim。
4. 无通用语法重写、标点清理或实体提取；相对半小时有解析，但title删除regex没有等价删“半”的分支，可能保留“半小时后”。空用待办提醒。

| delta | text:string | content追加，state=streaming，清statusText；有过程且createdAt有效时首delta记录thinkingMs |
| card | card:AgentCard | validCard校验十一type字段；append |
| suggestions | items:string[] | 替换suggestions |
| done | intent:Intent | 合法intent集合；state=done，清statusText；streamChat终止读取 |
| error | message:string | state=error，清statusText；streamChat终止；保旧再生成走fail恢复旧回复 |

SSE event名与JSON type一致（默认message可不另命名）；未知type或字段错误拒绝。plan允许1～8但不允许空数组，所以mock无计划时不发plan；id空串拒绝但没有额外trim id规则。step不能带pending作为事件status。卡片新增校验：itinerary要求id/title、每站time/title/detail/address字符串、合法point、route可选字符串；checklist要求id/title、groups.name与items字符串数组；forecast要求city/tip、label/condition/advice字符串、low/high/rain有限数值。没有额外语义日期／营业验证。

**step单向：**pending→running→done，也接受pending→done；done之后不会退回running，重复幂等，未知ID不造新step。不强制跨步骤依次执行或仅一个running；顺序进度来自mock发事件规则。后续plan不覆盖首计划，thinking在首正文后不继续，卡片内recipe.steps与route.steps不混成PlanStep。

**thinkingMs：**默认undefined；首delta时已有thinking或steps且助手createdAt可解析，记`max(0, event.at-createdAt)`；之后保持首值。它含等待与模拟过程传输，不是实际推理时长，也不是plan完成总耗时。显示秒数`max(1,round(ms/1000))`，无秒表刷新。首delta前stop／error／refresh不补耗时；首delta后保留已记值。

Chat默认折叠单一ProcessBlock：有thinking或steps才显示，展开同时显示二者；实时label为首个running标题或思考中；done有步骤且有耗时显示“已完成 N 步 · 用时 X 秒”，无步骤“已思考 X 秒”；aborted有步骤“已停止 · 完成 a/b 步”；error首个非done“第 k 步未完成”；时间兜底有值“已思考 X 秒”、无值“思考已中断”。done有步骤但耗时缺失也用中断兜底。非live的非done步骤显示未完成，刷新不把running冒充完成。

### 12.3 请求与流事件顺序

来源：Server／mockFetch、isRequest、chatStream、chunks。

- GET pathname以/api/home/overview结尾→JSON；POST以/api/chat结尾→SSE。request conversationId/query/city必须字符串、query非全白；history可省，存在则user/assistant与content字符串数组。不要求UUID或真实城市，也未用Server校验2000字（前端限制）。
- chatStream先createMockReply；plan标题赋ID s1、s2等，初始status“正在理解你的需求…”。
- 有thinking或plan：等随机80～160ms（slow另加5000）；有plan发plan→第一step running；thinking按chunks逐段发，每片等15～30ms。再补首正文等待至firstTokenDelay；多于一步则advance首步done、下一步running。
- 无过程：等首正文窗口一半，status“正在整理适合你的建议…”，再等另一半。
- 发多个delta，除首片外等20～45ms；正文中点如果尚非最后一步，advance。等到目标总时长后将剩余step依次done（advance可同时下一步running），再card→suggestions→done。
- chunks按Unicode字符Array.from切通常2～5字，末尾避免孤单1字；thinking也用它。不是逐token真实生成。
- 普通stop中断流，不补卡、不继续后续step；切页／菜单／历史／新对话不停止，事件仍归属原会话，跨页状态与停止入口见08。

### 12.4 时间与网络演示

来源：Server／chatStream、mockFetch；Client／lifecycle、searchForRequest、failOncePending；App／networks、setNetwork。

| 场景 | 规则 |
| --- | --- |
| 首页 | 随机450～900ms，不受slow延迟影响 |
| 首正文窗口 | 随机500～1000ms；有过程可能因分片传输超过窗口，非严格上限 |
| 目标总时长 | 随机3400～4400ms；若分片已经更久，不再等待负值，不是绝对时限 |
| 慢网 | mock_latency=slow；首窗口、目标总时长与过程前等待各在其相应规则加5000ms（总时间由真实串行等待决定，不能重复加成固定SLA） |
| 强制失败 | mock_fail=1约150ms后503，可影响首页与chat |
| 一次失败 | mock_error=once；Client仅chat消费，以mock_nonce或default区分；首页不消费。重试同nonce不再失败 |
| 随机失败 | failureRate或VITE_MOCK_FAILURE_RATE，限制0～1，非法0，默认0 |
| 超时 | 默认全生命周期20秒，包含headers、首段、完整正文；现有环境变量可调，本文未改配置 |

界面三选项原文／hint：正常网络／首字约 0.5–1 秒；模拟慢网络／首字约 5 秒，可体验停止；下一次请求失败／只失败一次，可体验重试。选项hint是UI文字，不替代上述实际等待规则；“首字约5秒”不是5000ms的精确承诺。

setNetwork先清mock_latency/mock_error/mock_fail/mock_nonce，再设置slow或一次失败新nonce；当前失败优先failOncePending，消费后恢复正常或slow；恢复正常清参数，保留其他search，不动环境。网络选项点击无成功Toast，恢复正常有“已恢复正常网络体验”。错误返回体与UI最终文案08第10节，不把JSON message当最终错误。

### 12.6 历史、再生成缓冲与viewState

来源：Store／load、settle、appReducer、AppProvider、newConversation；UseChat／send、stop；App／views、resumeId；Chat／ChatViewState、isGenerating、actions；Cards／CardViewState。

localStorage键lumi:v1，同存conversations/saved/theme/drafts/lastConversationId。无登录、限当前浏览器。加载草稿仅home/new/有效会话ID字符串、截2000；无效最近访问ID清空。首次成功接受发送才创建会话，标题首问前24字符串单位；create保留最近创建30段、清淘汰草稿。历史按updatedAt倒序，visit只记lastConversationId不更新排序；续聊优先busyId→lastConversationId→首条历史→/chat。侧栏最近对话不显示条数或本机说明，底部设置。

**完整done再生成：**previous保存旧Message；旧state保持done、正文/card/thinking/steps/suggestions不清空，statusText使其被识别为生成中。新Message在请求局部变量用同一applyEvent累积全部事件（含过程与耗时），不向UI逐片替换。status及running step标题可更新“重新生成中 · …”；done一次patch完整新结果。error／异常／stop恢复previous，清statusText、加“重新生成未完成，原回复已保留。{error}”或“已停止重新生成，原回复已保留。”。不重复用户问题、不改助手ID；重试历史截取规则第2.1节。

**普通错误／停止：**部分正文和已到过程保留；ending为“这次没能完成请求：{error}”或“已停止生成”，无旧专用重试面板，动作区“再试一次”／“重新生成”。追问只最后一条done且无statusText，不显示历史每条的追问。

**刷新：**settle pending/streaming→aborted、清statusText，已保存thinking/steps/thinkingMs保留；running步骤没有被补done，ProcessBlock呈未完成。done再生成因新结果仅局部缓冲，刷新仍旧done并清statusText，丢弃缓冲、不续传、不额外添加中断notice。

**当前会话viewState（非localStorage）：**scrollTop/follow、按消息ID的process开合、按`message.id:cardIndex:JSON.stringify(card)`键的expanded/mode/priceSorted/checked，切页或历史返回可恢复；数据改变不套用旧卡状态。刷新不恢复阅读、卡片展开／勾选、过程开合、表单或撤销槽。Composer草稿分区持久，成功接受才清、busy拒发保留。

### 12.8 清单直接填写与撤销

来源：Saved／saveItem、cancelForm、removeItem、SavedRow；Store／appReducer；UI／ToastProvider。

清单无Composer，不经过mock。事项trim1～80、备注原文最多300保存trim、设备本地datetime-local选填；无时间task，有有效未来时间reminder。UUID、done=false、ISO createdAt/可选dueAt；拒绝badInput、非法日期、≤当前、DST不存在时刻；DST重复按设备默认解析。确认前不创建，取消本次保留字段、清错恢复焦点；成功清字段、关表单、回全部、Toast；刷新不保表单。

点击删除立即；左滑先180ms退出（减少动效立即）再按最新id/index删除，右滑切done，不调用mock。独立8秒撤销跨页可用、恢复原id/index/done/日期，同id不重复；连续只最后条、刷新／超时丢撤销槽。卡片移除仅普通4秒Toast，无删除撤销；任何保存都不发系统通知。表单全部原文与ARIA见08第5、10节。
