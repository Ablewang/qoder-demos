## Q4 飞书消息读取能力

- 现状：日历和文档可以按用户身份读取。消息接口在自建应用加用户凭证的情况下能读到多少，需要实际验证。
- 验证方法：在 `.env` 的 `FEISHU_SCOPES` 里追加 im 相关权限，在应用里开通并发布后，运行 `npm run probe:feishu-im`。

## Q5 Google Cloud 权限

- 如果公司限制员工创建 Google Cloud 项目，就需要找 IT 申请，或者改用 IMAP 加应用专用密码（要看公司策略是否允许）。

## Q6 飞书卡片回调

- 背景：ADR-0011 计划由守护进程通过飞书长连接接收事件，因为本机没有公网地址。
- 如果卡片回调不能走长连接，就只能在 Web 控制台里审批，飞书里只发通知和跳转链接。

## Q7 桌面宠物形态（已关闭）

- 用户决定：做成“陪伴宠物，能协助日常办公”，并且有培养系统、能和鼠标交互、性格可以指定（名字、口头禅）、有自己的记忆。见 ADR-0012、ADR-0013。

## Q8 成长系统（已关闭）

- 用户答复：“1、2 都需要”。真实成长（见识、记性、默契、陪伴）和轻度养成（喂食、摸头、心情）都要，但养成不能带来任何负面后果（约束 I17）。具体数值和规则由 MOD-11 设计。

以下为当时的选项，留作记录：

- 总架构师建议：成长应该反映它**真实**掌握的东西，以及你们之间的默契，而不是额外的养成任务。
  - **见识**：接入的数据源越多，它知道的越多；
  - **记性**：记住的事越多；
  - **默契**：提议被采纳的比例越高；
  - **陪伴**：一起工作的天数。
  - 成长后的变化：解锁新动作和皮肤、台词更了解你。**不锁住功能，不惩罚**（约束 I17）。
- 可选的另一种做法：加入轻度的传统养成（喂食、心情值），但不能有负面后果。
- 已决定两种都做，以上是历史选项。

## Q9 宠物客户端技术（已关闭）

- 用户答复：“不懂啊，我想要兼容 macOS 和 windows”。这样就排除了 Swift；在 Tauri 2 和 Electron 之间，选更轻的 Tauri 2。见 ADR-0014、ADR-0015。

以下为当时的选项，留作记录：

| 方案 | 优点 | 缺点 |
|---|---|---|
| Tauri 2（Rust 外壳 + Web 前端） | 前端用 TS，和主体技术栈一致；比 Electron 轻得多；支持透明、置顶、点击穿透 | 要写少量 Rust；需要按像素判断哪里可以点、哪里穿透 |
| 原生 Swift（AppKit + SpriteKit） | 效果和资源占用最好；检测共享屏幕、全屏最方便 | 多一门语言；只能在 macOS 上用 |
| Electron | 生态最熟，全部用 TS | 内存占用大（常驻上百 MB），不适合一直开着的宠物 |

- 总架构师选择 Tauri 2；用户授权技术自评，平台可行性仍需实测。
