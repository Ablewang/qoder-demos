# ADR-0020 提醒幂等与通知隐私边界

- 状态：已接受，待实现与故障验证
- 日期：2026-11-19
- 决策者：总架构师（用户已授权技术自评）
- 补充：团子先行版协议 §6、§7；不改变公共 NoticeSink 签名

## 背景

代码复评发现：提醒投递期间取消会遗漏新通知正文并发布错误的 fired 事件；通知落库后、提醒关联前中断会在重启时重复投递；去重合并会降低敏感度、丢失依据。聊天的凭证过滤不能保护直接 REST 或模块调用入口。

## 决策

1. 通知与提醒在各自持久化边界校验疑似凭证文本。通知标题、正文、原因、下一步以及 facts 的标签、字符串值、单位和引用均需校验；提醒正文也需校验。检测规则与先行版记忆/聊天相同；拒绝时不得写库、发布事件或输出原文。凭证值不能通过 dedupeKey、links 或 evidence id 等字符串元数据写入数据库。
2. 普通通知去重仍遵守已有时间与状态规则，但合并后的敏感度只能取历史、输入和记忆依据的最高级别，依据按完整引用去重并保留；不通过低敏新输入洗掉历史高敏来源。事实正文不改写。
3. `companion.reminder` 的 `dedupeKey = reminder:<id>` 是单次提醒的持久投递键，不使用普通未读/忽略时窗去重。在通知模块新增迁移版本建立 `rt_notice_receipts`，保存唯一投递键、通知 id、首次创建时间等无正文回执；首次通知和回执在同一同步事务提交。重试不增加 count、不再触发通知/气泡钩子，返回既有通知。
4. 通知正文仍按既有 30 天保留。清理通知不清理无正文幂等回执；已清理通知的重试返回原 id 的无正文过期摘要，不重新建立通知或再次投递。旧合法提醒通知在新迁移中回填回执；历史重复记录不自动删除。
5. 扫描器投递前重新检查提醒仍为 scheduled，投递返回后用条件更新并检查 changes。取消若发生在投递途中，扫描器必须清理新创建通知及事件历史中的提醒原话，不发送 fired 或含原话的 reminder.changed。取消前已送达的事件不可追回，但取消后的状态和持久历史不得继续包含原话。
6. 所有上述变更保持本机、无模型、无数据源、无对外写入。客户端在收到取消状态或清理后的通知更新时移除对应气泡与本次运行的关联卡片正文，不能只依赖数据库擦除。

## 验证门槛

- 延迟 submit 后取消，放行 submit：提醒仍 cancelled，通知与事件历史不含原话，无后续 fired 事件。
- 通知提交成功后故障，先标已读/忽略再重启：同一投递键仍只有一次创建事件与通知；通知保留期结束后也不再次投递。
- secret → normal、confidential 记忆依据 → normal 合并不降敏且依据保留。
- 各入口与字符串字段的合成凭证样本均在持久化/事件/钩子之前被拒绝，日志不得带样本正文。

## 影响

增加少量不可丢弃的无正文投递回执。删除回执不属于通知正文清理；整个数据库丢失不保证跨故障幂等。取消不承诺撤回用户已经看见或外部保存的内容。
