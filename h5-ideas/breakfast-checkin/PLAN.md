## 一、结论先行

推荐做一个**“来吃早饭，顺手打个招呼”的熟客名单工具**，而不是老人安全监测系统。

1. 对外入口是吃早饭、打招呼；MVP 的核心是当天到店记录、请假、店主核对和人工联系。不要把“报平安”解释成系统确认健康或安全。
2. **不以“订明早”作为首版主入口**。预订可作为第二阶段的独立可选功能；购买、预订和参加邻里关心计划互不绑定。
3. 首版**完全不自动向守护人发消息**，但也不只给老板一张灰色名单：必须有每日核对、待关心事项、负责人和联系结果。
4. 默认连续 **2 个约定营业日**缺少记录才进入人工核实；由老人选择 1／2／3 个约定营业日。当天出现真实危险迹象时，不等待这个阈值。
5. 当前直接开发假数据单店内测原型，模拟一位店主和一位授权替补；真实店铺未找到只阻止真实运营，不阻止本地代码。真实试点仍须另行授权、找到负责人和替补并先做线下验证。
6. 技术倾向 **melo-cli fun 的 Node 24 后端 + 托管 MySQL**，前提是能核实面向大陆老人可访问、数据及运维位置合规、费用和退出机制明确。Qoder Sites 是交付更短的候选，不因“托管”就默认隐私边界已经成立。
7. 老人免注册账号，不等于没有身份验证。公用店铺码不含老人名单或授权信息；四位数只可作为现场辨认辅助，不能作为访问秘密。
8. 不收集定位、家庭地址、身份证、健康情况和照片；不公开老人名单；不许诺必达、必看、及时救援或“保平安”。

### 2.1 “订明早”与“报平安”的专项论证

| 维度 | 预订为入口 | 报平安为入口 | 推荐的早餐打招呼入口 |
|---|---|---|---|
| 老人已有习惯 | 部分熟客才有提前预订需求 | 可能被理解为每天向子女交作业 | 原本买早饭时顺手说一声，老板可代点 |
| 老板收益与负担 | 可能利于备货，也可能增加订单处理 | 缺少直接收益，靠熟人关系支撑 | 把已有的“留意熟客”变成可核对的名单 |
| 身份与尊严 | 商业理由自然，但不能隐瞒关心用途 | “我还在”可能让人想到衰老和死亡 | 店内叫“熟客打招呼”，不标“独居”“重点老人” |
| 数据有效性 | 昨晚下单不等于今早到了 | 在家点击不等于到店，更不等于健康 | 到店由本人主动记录或店员当面代点，仍不验证位置 |
| 首版范围 | 需要商品、数量、截单、取消与备货单 | 需要解释误报、提醒和责任 | 保留最小记录与人工核实，预订独立延后 |
| 风险 | 为了享受预订被迫交守护人信息 | 把一个点击当作安全证明 | 明确“只是到店记录，不是安全判断” |

**推荐不是把关心功能藏起来。** 招募时直说：“几天没打过招呼，老板会在约定时间核对一下，再联系你指定的人；忙不过来或断网时也可能漏看。”不同意照常买早餐。老人不用手机、没有买东西、忘带手机，都可以参与或拒绝。

第二阶段是否上预订，由实际需求决定：如果至少 5 位参与熟客确有稳定预订习惯，店主确认名单比微信更省事，再增加 2～3 种早餐、明日数量、截单时间和取消入口；不接支付，不收费保证关心服务。预订永远不自动产生到店记录。

## 三、产品范围与运行规则

### 3.1 三个阶段

- **M0：一周线下流程验证。** 取得双方同意后，用店主保管的纸张记录少量熟客，按固定时间核对和电话联系；不把真实资料上传到演示网页。
- **M1：单店数字 MVP。** 店铺码、登记与同意、设备绑定、到店记录、老板代点、请假、营业日设置、核对名单、人工关心事项、退出删除、故障提示。
- **M1.1：预订验证版。** 只有试点显示真实需求才做预订及备货单。

首版不做多店平台、子女签到轨迹看板、排名连续打卡、AI 风险判断、健康问卷、自动上门、自动报警、公开家庭群推送、支付和广告。

### 3.2 记录究竟代表什么

- 记录是“某日有人为这位熟客提交了到店记录”，区分**本人填写**与**店员当面代点**。
- 老人按钮推荐改为“**我今天来吃早饭了**”，而不是让系统显示“安全”“健康正常”。“报平安”可作为口头表达，不能成为系统判定。
- 静态店铺二维码可能被拍走，H5 不定位，不能证明扫码者确实在店里。本人填写不是到店位置证明；店员代点也不是健康评估。
- 没有记录只表示**没有记录**，不表示没吃饭、失联或发生危险。
- 不能因昨天预订、守护人打开链接、老板打开名单、历史记录或缓存页面而生成今日记录。
- 默认只显示日期与填写来源，不给家属展示精确到店时刻或行踪轨迹。

### 3.3 缺记录的计算口径

1. 店铺时区固定为 `Asia/Shanghai`，日期由后端确定，不相信手机时间。
2. 店主确定营业日与每日核对时间，示例为 11:30；以实际营业习惯为准。
3. 老人报名时确认其约定到店日。首批选择每周通常到店 5～7 天的人，不以年龄、疾病或子女焦虑推断到店规律。
4. 新登记从下一个约定营业日开始观察，不追溯历史缺席。
5. 非营业日不累加缺记录次数；事先登记的请假日打断连续缺记录，假后重新从 0 开始，不补发假期提醒。
6. 店主在核对前先补上真实见到、但忘记代点的记录，再确认“今天名单核对完了”。未核对或系统故障的日子是**未知**，不能直接当缺席累加；连续计算中遇到未知停止可靠推断，进入“资料不全，请人工确认”区域。
7. 在核对时间以后，连续 N 个有效的约定营业日缺记录，才生成“待人工核实”事项。默认 N=2，允许老人选择 1／2／3，修改规则不追溯制造旧提醒。
8. 同一段缺记录只保留一个未结事项，不每天发一遍。店主打开联系页时重新读当前状态，防止晚到、补记或新请假后仍通知。
9. 临时闭店、负责人缺席、无法核对，应显著标注服务暂停或记录不完整，走人工备用流程，不悄悄把所有人标成缺席。

例子：周一、周二都是约定营业日，两日核对后都无记录，周二才进入人工核实；周日闭店不会多算一天；周一至周三请假，周四开始重新计数。提醒文案给出具体日期或“两个约定营业日”，不把跨休息日的情况说成“连续两天没出门”。

### 3.4 人工不是临时替代，而是首版设计

- 主责人每天固定核对一次；建议自行设置手机系统闹钟，**这不是 H5 推送能力**。
- 一位授权替补知道当天如何接手；不开群广播，也不默认其他店员可以看联系方式。
- 常规名单争取每日额外工作 5 分钟以内；需要电话的日子可能增加 10～30 分钟，必须实测，不能宣传“零负担”。
- 联系前先问自己：是否漏点、店休、请假、晚来、规则不适合？核实后才拨守护人电话。
- 记录“谁在什么时间做了哪一步”，不记录老人疾病、家庭纠纷或电话录音。
- 无人愿意承担每日核对和替补，不启动真实服务。对用户的承诺只能是约定操作流程，不能是结果保障。

## 四、技术方案

### 4.1 前端

推荐 **Vite + React + TypeScript + 原生语义 HTML/CSS**，只加必要的路由和二维码生成依赖。

- 老人端与店主端同一前端、不同权限；不使用面向后台的密集表格作为老人页面。
- 页面静态构建，业务请求走同源后端；部署后不依赖开发者电脑持续运行。
- 本地存储仅存字体偏好和非敏感提示，不存守护人电话、完整名单或真实测试样本。
- 不以 PWA 安装、Web Push、微信登录或自定义微信分享为首版前置条件。
- 请求未成功不能出现绿色“已记录”；不离线排队补传签到。弱网时保留操作意图，先查询服务端是否已保存，避免重复写。
- 包管理遵从最终选定脚手架与现有项目约束，不在方案阶段修改全局配置。

### 4.2 后端候选比较

| 维度 | Qoder Sites 后端 | melo-cli fun 项目 | 自建大陆服务器 + 数据库 |
|---|---|---|---|
| 拟用形态 | 静态前端 + Deno/Edge Function + Function-owned 私有数据库 | 静态前端 + Node 24 Lambda/API + 托管 MySQL | 同源静态前端 + Node API + MySQL/PostgreSQL |
| 优势 | 发布、Functions、Secrets 与数据库管理一体，独立开发交付路径短 | 常规 Node 生态和 MySQL 模型，应用身份与事务实现更直接；已有快速交付工具链 | 服务位置、备份和认证实现更可控 |
| 必须核实 | 真实区域、分包商/运维访问、费用与配额、凭证转发、数据库隔离、备份删除和导出 | 用户账号是否有权限、模板/SSO/GitLab 依赖、公网路由、数据库地域、连接数、费用、备份/日志政策 | ICP 等适用要求、安全加固、备份、监控、故障维护、持续付费与维护人 |
| 老人身份 | 公共入口 + 应用自己的受限身份，不要求老人有 Qoder 账号 | 应用自己的设备凭证和店主授权 | 应用自己的设备凭证和店主授权 |
| 数据访问 | 必须走 `function_backend`，数据库租户隔离之外还要 Function 按店铺、角色、对象鉴权 | 数据库只供后端访问；参数化查询与角色校验，禁止前端直连 | 同左，由运营方自己负责配置与证明 |
| 原子性 | 已有文档支持唯一键/条件更新；多次 SDK 请求不是事务，不能假定有任意 SQL/RPC 能力 | 采用 MySQL 事务、唯一键和版本条件更新，需验证所用驱动及托管环境 | 能实现，但运维成本更高 |
| 定时任务 | 已读资料不能证明有适用于该产品的托管日程；首版不依赖 | 不能由 Lambda 名称推断已有 cron；首版也不依赖 | 可以部署任务，但首版没有必要 |
| 主要风险 | 静态“可访问”不等于私有接口隔离；不能为了免登录开公开数据库 CRUD | 默认网络为 `internal`，不能直接给外部老人用；不能由配置里存在中国生产枚举就断言当前应用已部署大陆 | 一个人很容易低估持续运维和安全责任 |
| 费用结论 | 尚无当前账号报价，不能承诺免费或额度足够 | 尚无该应用报价，不能把内部平台资源视为永久免费 | 相对明确但有持续资源和运维费用 |

**推荐顺序：** 先完成线下验证；若现有 fun 权限、合适数据地域和公网访问可核实，采用 fun。若 Qoder Sites 更快且能实际通过同等的数据/身份/退出检查，也可选 Sites。两者均不能满足时，继续纸笔或无真实数据原型，不自动改用境外免费数据库收集老人资料。

本阶段仅阅读工具资料，没有执行 `fun init`、`fun deploy`、数据库申请、Sites 开通或发布。

### 4.3 平台实现注意事项

**fun：** 拟选择 Node 24 后端、Vite React 前端和明确的外网入口。数据库申请必须匹配实际配置中的基础设施环境，不手工猜地域；部署 stage、公网可达、数据库实际落地位置是三个不同事项。敏感配置通过安全的运行时 Secret/环境注入，不写入源代码、前端环境变量或聊天。正式数据不能进入不明用途的测试库。

**Sites：** 拟采用新建项目的 `function_backend`，不复用 legacy 匿名公开 CRUD。入口是 HTTP Edge Function，不启动 Express 常驻服务或后台计时器。应用 Cookie/Authorization 的转发与响应保护、直接 Provider 绕过风险必须实测；否则免账号鉴权可能失效。数据库日期在当前受限 SQL 下应使用经过校验的 `YYYY-MM-DD` 文本，不能直接套用 MySQL 的 `DATE`。不要把不同 SDK 调用说成一笔数据库事务。

### 4.4 架构与接口职责

```text
店铺公用码 ──> 公共入口：店名、说明、报名/找老板
                          │
老人已绑定设备 ──受限会话─> 同源应用 API ──> 私有数据库
                          │                 店铺/本人范围校验
店主授权设备 ──店铺权限───> 同源应用 API ──> 当日名单/人工关心事项
                          │
                          └─首版无对外自动发送、无位置采集
```

拟议接口覆盖：读取本人的今日状态、登记草稿与双方同意、提交/查询今日记录、请假/撤销、读取店主当日名单、代点/纠错、完成每日核对、领取/更新人工关心事项、撤销设备、退出与删除。公用入口只读店铺公开信息，不能按称呼检索老人。

写操作均校验方法、数据大小、字段和角色。日期、店铺权限、记录主体由服务端受信身份确定，不接受浏览器传来的任意 owner/staff/resident 身份。每次敏感读写都检查当前授权与撤回状态。

### 4.5 数据模型：逻辑模型，不在本阶段写 SQL

| 实体 | 最小字段 | 约束及用途 |
|---|---|---|
| `shops` 店铺 | id、店名、公开营业联系渠道、时区、通常营业日、核对时间、服务启停状态 | 不保存店主家庭地址；单店首版，不建设商城 |
| `staff` 授权工作人员 | id、shop_id、显示称呼、角色、启用状态 | 店主和指定替补；撤销立即限制新请求 |
| `residents` 熟客 | id、shop_id、称呼、可选辨认尾码、约定到店日、阈值、参与状态、版本 | 不保存身份证、年龄、健康标签、家庭住址或老人手机号码；状态含待同意、有效、暂停、退出 |
| `guardians` 守护人 | id、resident_id、称呼/关系、加密联系方式、同意状态、同意版本/日期 | MVP 每位熟客 1 位指定守护人；守护人本人也须知情接受。不同意则不能默认启用联系服务 |
| `consent_events` 同意证据 | 主体类型/对象、文案版本、同意/撤回时间、方式、协助见证 staff_id | 老人同意与守护人同意分开；无默认勾选、无录音、无照片 |
| `daily_records` 每日记录 | shop_id、resident_id、业务日期、记录来源、有效/撤销状态、操作者、版本、操作请求标识 | 同一店铺/老人/日期唯一；无记录由查询推导，不能造一条“老人不安全”数据 |
| `shop_days` 营业日核对 | shop_id、业务日期、开门/闭店/未知状态、是否核对、核对者、核对时间 | 区分真实缺记录与店休、没录全、服务故障 |
| `leaves` 请假 | resident_id、开始/结束日期、有效/取消状态、操作者、版本 | 不保存“去儿子家”“住院”等自由文本；仅保存暂停联系的日期 |
| `care_tasks` 人工关心事项 | shop_id、resident_id、该段缺记录标识、依据日期、状态、负责人、处理时间、最小结果分类、版本 | 同一段缺记录只有一个进行中事项；区分待核实、待联系、联系中、跟进中、结束、取消；不是消息必达记录 |
| `device_sessions` 设备会话 | 随机凭证摘要、角色/对象范围、过期时间、撤销状态 | 不存原始凭证、不做设备指纹；绑定与登记状态不能混用 |
| `operation_audit` 最小操作记录 | 操作者、对象、动作类别、时间、请求标识 | 只为纠错与责任追溯，不记录电话内容、Cookie、Token、完整联系方式或定位 |
| `reservations` 预订，第二阶段才建 | resident/customer 范围、店铺、取餐日期、商品和数量、截单规则版本、预订/取消状态 | 与到店记录解耦；无预订也能打招呼；不参加关心服务也能预订 |

实现时为店铺/日期、熟客/日期、未结关心事项建立必要索引；使用数据库唯一键，不能只靠前端禁用按钮防重复。联系方式仅在授权人员需要联系时由后端解密。

### 4.6 一致性与纠错

- 每日记录幂等；同一次不确定提交用原请求标识查询，不换标识盲目补写。
- 店主和老人同时提交，以数据库唯一键收敛，不生成两次签到；保留来源规则和必要操作痕迹。
- 不允许“一键全部到了”；代点只在当面见到人后逐个操作。
- 误点可以撤销；界面显示操作已撤销，不悄悄删除证据或补造健康结论。
- 请假与联系任务可能并发：拨号前重新读取当前状态；请假/新记录后取消尚未联系的事项。已经发出的人工电话无法收回，需要补充更正。
- fun 可用事务保存需要原子完成的状态；Sites 如需多步骤，明确草稿/待激活状态，全部同意和条件验证完成后才激活，不假定跨表操作天然原子。
- 请求失败、名单读取失败不是“今天无人到店”；界面显示未知并指导店主用纸笔，不能返回一个看似正常的空名单。

## 五、免账号身份与权限

### 5.1 老人：现场协助绑定，不公开花名册

1. 第一次扫码只看到店铺说明和“找老板帮我登记”；老人可选择本人操作，也可以全程由老板协助。
2. 老人听懂并表示同意，店主建立待激活登记，守护人本人也接受后才能启用缺记录联系。
3. 有手机者，由店主当面发放一个短时、一次性的高熵设备绑定码/二维码；完成后兑换为只属于这位老人的受限会话。无手机者不绑定，照样由老板代点。
4. 浏览器使用 `Secure`、`HttpOnly`、适当 `SameSite` 的会话 Cookie，凭证为密码学安全随机数，后端只存摘要。写请求防 CSRF；不把长期秘密放在 URL、localStorage 或分享海报里。
5. 绑定链接避免进入日志/第三方分析，设短时失效并用一次即作废。展示的公用店铺码永远不是绑定码。
6. 老人会话只可操作自己今日记录、自己的请假及退出，不可看其他老人或守护人的联系方式。

“店铺 + 称呼 + 四位数”便于同名辨认，但总空间太小，又常被熟人知道，**不能当认证**。丢手机、换微信浏览器或清 Cookie 后，老人找老板当面重新绑定，旧设备撤销；不能凭称呼在线找回。

### 5.2 店主、替补和守护人

- 店主与替补分别授权设备，身份独立、可撤销，不把店主私密码写在店铺码上。
- 首店可用受控设备配对避免老人账号体系；店主账号/设备发放仍属于管理员工作，不能开放匿名注册店主。
- 联系方式列表默认遮挡；点击具体待处理事项才显示需要的号码。店主手机必须有系统锁屏，离店不放在公用台面。
- 老板权限仅限本店；替补只接触其职责所需信息。临时帮忙的人不能默认获得全名单。
- 首版守护人主要接人工电话/私聊，不提供老人连续轨迹看板。若使用确认邀请页，邀请只用于本人接受与查看自己的联系约定，短时单次；不凭收到转发链接取得管理权限。
- 设备凭证证明“持有该受限设备”，不是证明实名或确认本人安全。被盗风险必须用限权、撤销与现场恢复降低，不能宣传不存在盗用。

## 六、提醒渠道比较

### 6.1 首版渠道决定

**老板或网格员人工电话为主，已建立且双方愿意使用的微信私聊为补充。** 系统不代发，店主手动拨号/复制最小文案，并记录是否接通和是否仍待跟进。

人员是否阅读或接通、老人是否安全是不同问题。人工联系也可能忙忘、无人接、号码过期；因此要有核对人与替补，而不是说“人工最可靠”。

### 6.2 成本、资质与技术边界

| 渠道 | 费用口径 | 资质/前置条件 | 不能承诺什么 | 适用结论 |
|---|---|---|---|---|
| 人工电话/微信私聊 | 系统消息费为 0；电话套餐、店主工时、替补成本另计 | 双方知情；授权工作人员；已确认的联系方式与排班 | 不保证按时看名单、接通或核实安全；复制文案不等于已发送 | MVP 推荐，先验证人的闭环 |
| 微信服务号订阅/模板消息 | 账号认证及可能的服务费用，需核实当前主体与平台规则；不能写“免费无限发” | 认证服务号、相应接口权限、匹配行业与用途的模板、守护人授权；四种机制见下文 | H5 可在符合条件的微信网页接入订阅通知，但不具备通用、每天必达的微信推送 | 仅做后续候选，资格与模板未确认前不排入承诺 |
| 企业微信群机器人（消息推送） | 官方帮助页未载明此接口单独收费；不能推导企业微信整体零费用，还包括群维护与人员成本 | 仅企业微信内部群；管理员允许创建、群管理设置允许；接收者需是该内部群成员；Webhook 是服务端秘密 | 不支持外部客户群或普通微信家庭群；每个机器人最多 20 条/分钟，接口成功不等于已读或已处置 | 更适合已有企业微信的授权工作人员协作，不作为全体家属渠道 |
| 国内短信 | 小量通知短信参考 0.045～0.050 元/计费条，套餐可能需一次购买 1,000 条；实际报价及拆分见下文 | 供应商认可的单位资质或有效授权、实名报备、签名、模板与用途审核、守护人独立同意 | 回执不等于本人阅读；个人账号认证不等于具备可用发送资质；拦截、停机和延迟仍存在 | 自动化第二阶段候选，不作为急救或唯一渠道 |

短信预算公式：`计费条数 × 当前获批单价 + 必要固定费用`。2026-11-17 查询的阿里云国内通知短信公开价，月发送量不超过 10 万条时按量为 0.045 元/条；1,000 条套餐为 50 元，常规有效期两年，实际订购价与有效期可能因活动不同。小量预算可参考 0.045～0.050 元/计费条，不能套用百万条档报价。若 15 人、每人每月 2 次关心、每次一条，30 条消费仅约 1.35～1.50 元，但套餐可能仍须先支付 50 元；这只是量级示例，不是缺记录率预测。含签名超过 70 字的中文短信可能拆分计费，补发与变更通知另计；首版不采购短信。

阿里云当前资质页明确：个人认证的自用资质无法完成签名实名报备，需要合规他用资质及授权，或升级企业认证；套餐页写“个人用户可申请通知模板”不等于完成发送资质。店铺/合作主体的营业或组织证照、授权、签名、模板和运营商审核需逐项确认，产品创意名不能自动作为合规签名。资质审核约 2 个工作日、运营商报备常见 5～7 个工作日，部分 7～10 个工作日甚至更长，均不作为上线时限保证。所需单位证照直接提交供应商审核，不放进老人业务数据库。该供应商还要求国内短信由中国内地 IP 发送，因此后续选用时必须核实后端出口，不能只看网站可访问。

**微信的四种机制不能混写：**

| 机制 | 资格、用户动作及能力边界 | 本产品判断 |
|---|---|---|
| 服务号一次性订阅消息 | 认证服务号并确认接口权限；微信网页可拉起授权，未关注也可授权；每次有效授权对应一次发送，同用户同 `scene` 重复授权不能累计 | 不适合假设一次报名就能持续关心；具体旧接口是否对该账号开放需确认 |
| 服务号模板消息 | 认证服务号、合适行业与模板；接收者为该账号关注用户的 OpenID；这是有真实服务关系、用户接受或可合理预期的服务通知，不是每条一次性订阅授权 | 是否允许向守护人发送早餐缺记录通知需平台审核；不能用订单模板伪装安全提醒 |
| 服务号订阅通知 | 认证服务号开通功能、选合适类目与模板；微信网页需安全域名及订阅组件；一次订阅发送一条，长期订阅仅向政务民生、医疗等公共服务领域开放；关注与未关注的通知位置不同 | H5 存在合规接入路径，但普通早点铺不因“关爱老人”自动获得长期模板；必须确认实际账号资格 |
| 小程序订阅消息 | 属于小程序而非普通 H5；一次性与限定公共服务类目的长期订阅分开，保留用户选项不等于取得长期权限 | 不把小程序能力当成当前网页已具备；另做小程序属于新增范围 |

企业微信帮助页说明“消息推送”仅支持内部群，外部群暂不支持，且当前不支持可靠的 @ 成员提醒；即使 API 文档出现相关字段，也须实测客户端效果，不能写成已读确认。只发送授权工作人员需要处理的最小事项，不把老人名单或守护人电话推到扩大可见范围的群。

对所有自动渠道区分：API 接收、供应商/运营商送达回执、收件人阅读、实际联系核实。四者不能互相替代，也不能由回执证明老人安全。人工微信只允许负责人手动私聊/复制文案，不用个人号外挂自动群发。

### 6.3 对原始技术说法的修正

- “H5 发不了推送”应改成：Web Push 在部分浏览器/系统具备条件，但受授权、安装方式、微信内浏览器与系统支持限制，**不能当本产品跨手机的可靠基线**。
- “服务号每条都要订阅”过于笼统，需要区分服务号一次性订阅消息、模板消息、订阅通知及小程序订阅消息。H5 可在满足认证、安全域名、模板与用户订阅要求时使用服务号订阅通知；不能从小程序养老/民生类权限或一次报名推导普通早点铺的长期通知权。
- “企业微信群机器人能发到家庭群”不能泛化成普通微信群。即使社区已有企业微信，也要确认实际群类型、机器人资格和接收方，不能公开发布老人缺记录名单。
- “短信最可靠”应改成：短信覆盖面相对广，但发送成功、平台回执、送达手机、本人阅读、实际完成关心是不同状态。

### 6.4 若以后增加自动消息

先保留人工核实，再选择一个获准渠道，不能一次接齐所有通道。使用服务端 Secret、固定收件范围、单一事项去重、限频、已撤回检查和发送前最新状态检查。保存发送/回执/人工确认的区别，不自动把“发送成功”标为“已关心”。

未送达、接口失败或状态不明转给负责人；不能盲目多通道群发或不断重试。云端定时触发、持久化队列、运行失败告警及休假排班需单独完成能力验证与开发，不能用浏览器打开页面时的计时器代替。

## 七、数据最小化与隐私

### 7.1 不收集与不公开

- 不收集地理位置、家庭住址、身份证、照片、人脸、健康数据、老人电话、通讯录、电话录音、旅游/就医原因。
- 不把“独居”“失能”“高风险”作为产品标签。首试点选择能自主知情同意的成年人，不把 60 岁以上等同于缺乏同意能力。
- 不设公开花名册，不展示给其他熟客，不把守护人联系方式拼进二维码，不给子女自动开放历史轨迹。
- 不接广告 SDK、第三方行为分析或 AI API处理真实资料。使用请求级、脱敏的故障日志，而不是抓取完整页面和请求体。
- 请假只保存开始/结束日期；口头告诉老板的原因不录入系统。

### 7.2 同意、主体与访问

上线前写明谁是个人信息处理者：例如实际试点运营主体；店主、开发运营方、社区与云服务商之间的职责，按真实安排约定，不能凭名字认定谁只是“代管”。称呼、到店记录和守护人联系方式均属于可关联个人的信息，免费、小店、十几人试点不当然免除个人信息保护义务（《个人信息保护法》第 4、6、14、17、19 条）。

60 岁以上本身不等于法定敏感信息或缺乏同意能力；但长期与特定店铺关联的到店日期，可能形成行踪轨迹或暴露特定身份，**不采 GPS 不等于绝无敏感信息风险**。正式收集前评估具体记录与推断用途；如认定涉及敏感信息，落实特定目的、充分必要性、严格保护、必要性/权益影响告知与单独同意（第 28～30 条）。本产品不以增加同意勾选来为不必要的监控功能开绿灯。

共同决定目的和方式的主体按共同处理约定权利义务；仅按指令处理的云服务商或开发方，按委托处理约定期限、范围、安全、监督、返还/删除和转委托安排（第 20～21 条）。店主内部授权、向社区等独立处理者提供信息、家属个人家庭事务场景不是同一种关系，按实际安排复核；“守护人”只是联系人称呼，不自动赋予法定监护权。

委托处理、向其他处理者提供信息、敏感信息及可能的出境等情形，依法事前做个人信息保护影响评估并记录处理情况（第 55～56 条）。法规对出境手续可能有特定豁免，但不能据此推定免除告知、单独同意、评估等仍适用的义务；首版不以境外免费服务作为默认方案。

- 老人自己同意参加与共享必要的缺记录信息；守护人本人同意联系方式被保存、接受该用途的联系。
- 不能让子女替有自主决定能力的老人一键报名；不能让老人一句同意就替代守护人对其本人电话处理的告知。
- 提供目的、范围、接收方、存储期限、风险、退出入口及投诉联系渠道；涉及向独立第三方提供个人信息时，按适用要求取得相应单独同意。
- 引入社区或换云供应商不能自动扩大访问权限；需要重新评估目的、接收方与告知/同意安排。
- 跨境、境外运维或分包商访问不能用“服务器在国内”一句话排除。首版优先不发生这类流转；若不能核实，不上传真实资料，先做合规评估。

### 7.3 拟定保留与删除规则

以下日常业务数据期限是试点建议上限，不是法定期限；正式采用前由实际运营主体确认必要性及可执行性。法律要求另行保留的资料单独、受限管理，不能套用日常记录删除期限，也不能因此延长全部到店历史的保存。

| 数据 | 推荐保留 | 退出/删除 |
|---|---|---|
| 日常到店/请假记录 | 滚动 30 天 | 退出后停止新处理，7 天内完成在线删除 |
| 守护人联系方式、参与档案 | 参与期间，只为该项联系使用 | 撤回即停止新联系、撤销访问；7 天内在线删除 |
| 人工关心事项与最小操作日志 | 滚动 30 天 | 不无限保留日常记录；未结事项退出时停止该产品流程并作必要告知 |
| 同意/撤回的最小证据 | 参与期间；退出后是否保留及期限须明确合法依据，建议评估不超过 90 天；依法构成影响评估处理记录的部分另行归档 | 不能以“可能担责”为由永久保存。无必要依据则随退出删除；不保留日常轨迹或完整电话 |
| 个人信息保护影响评估报告和处理情况记录 | 《个人信息保护法》第 56 条要求至少保存三年；具体归档范围与起算由合规复核确定 | 与日常业务库分开、最小化、限权归档；不能承诺退出后一并在 7 天内删除；法定留存不授权继续联系或使用到店历史 |
| 备份 | 建议滚动不超过 7 天，能力待核实 | 向用户说明删除副本的实际最长周期；恢复时先应用删除清单，不让退出资料重新可用 |
| 纸质备用名单 | 仅当前试点必要资料，锁闭保管 | 退出后同步删去，试点结束按约定销毁 |

联系方式服务端加密，密钥与数据库分离；HTTPS、最小角色权限、数据库不对浏览器开放。加密只是降低泄露后果，不替代合法目的、同意或访问控制。

数据泄露时暂停有风险入口、撤销受影响凭证、查明受影响范围、按适用法规采取补救和报告/通知；不能要求老人以“已同意免责”为由接受泄露后果。

## 八、页面与交互设计

### 8.1 老人端统一可用性标准

- 针对 60 岁以上实际测试：正文建议 22～24px，主操作 28～32px，触控区至少 64px 高，主要操作一个屏内可见。

### 9.1 产品声明草稿

> “早点铺我还在”是小范围试用的熟人互助记录工具。它记录参与者自愿提交或当面由店员代填的到店信息，并帮助授权人员按约定人工核对、联系指定的人。

> 参加完全自愿，随时可以暂停或退出，是否购买或预订早餐不影响选择。运营方应依法保护资料、处理投诉和纠正错误。本声明不排除法律规定不能免除的责任，也不要求参与者放弃其法定权利。

这是一份**服务范围与风险说明，不是免责金牌**。不能写“发生事故一概与我们无关”“勾选后自担全部后果”。《民法典》第 506 条规定，造成对方人身损害、因故意或重大过失造成对方财产损失的免责条款无效；第 496～497 条要求公平制定、显著提示和解释相关格式条款，并限制不合理免责。实际宣传、运行承诺、履行状况、过失、因果关系、信息保护和店铺自身场所安全义务等仍影响责任，不能只靠产品命名切割。以上是方案风险识别，不是个案法律结论；上线前由熟悉个人信息与民事责任的专业人员复核具体文案与协议。

### 9.2 误报处理

```text
达到阈值/资料不足
  → 指定人员核对原始记录、闭店与暂停情况
  → 找到漏记/晚到：更正，取消未发联系，保留最小操作痕迹
  → 尚不清楚：本人约定的联系人先私下问候
  → 已经打扰联系人：立即补充更正，不用“已安全”结案
  → 只录结果类别；询问老人是否需要改约定日/阈值
```

不得每次误报后擅自提高阈值、责备老人或要求证明行踪。连续两次因流程漏记误报，暂停扩员，检查店主录入负担及时间安排；必要时暂停数字联系功能而保留线下问候。

| 本人或店员误点导致漏关心 | 撤销错误记录，人工重新核对与联系；保留最小操作轨迹，调整交互，禁止批量打勾 |
| 联系方式失效/对方拒绝 | 联系服务转为暂停，老人重新指定且新联系人同意后才恢复；不暗中换收件人 |
| 未接通或守护人暂时无法确认 | 事项保持未结，由主责人与授权替补继续约定流程；不能以“拨过一次”判定安全 |
| 已知发生真实紧急情况 | 现场人员/家属按既有应急办法求助，例如医疗急救 120、需要警方协助时 110；不等待阈值、不让网页指挥开锁、破门或自行医疗处置 |
| 用户投诉或事件可能与遗漏有关 | 保存必要事实与受限证据，暂停扩员/相关流程，通知实际运营主体，复盘及依法处理；不销毁日志、不以声明推卸法定义务 |

上门只能由老人同意的现实熟人或有职责人员依实际情况开展，系统不储存地址、不公开寻人、不提供“无人答应就破门”的建议。没有到店记录本身不构成自动报警依据。

### 9.4 其他主要风险及上线闸门

| 风险 | 必须满足的措施 |
|---|---|
| 被监视、伤尊严 | 无独居/高风险标签，无排名，老人自己决定，可不解释请假原因 |
| 账号免注册导致隐私泄露 | 现场受控配对、角色/对象限权、公用码不带名单、设备可撤销 |
| 对老板依赖过高 | 具名主责、替补、核对时间及离岗暂停办法；没有接班人则不提供持续联系服务 |
| 数据跨境/不知谁负责 | 核实实际服务链、接收方、处理者与受托安排；不明则不用真实资料 |
| 闭店/假期造成连续误报 | 营业日与暂停规则先行，不把未知当缺席 |
| “意义感”掩盖商业强绑 | 报名独立于预订与消费，无不参加加价、曝光或服务区别 |
| 联系被冒用/诈骗 | 固定授权人员、可回拨的店铺/运营联系渠道，不索要验证码、钱款、住址或健康细节 |

## 十、线下试点方案

### 10.1 怎么找店

优先用户认识的店，而不是线上广撒邀请。选择老板认识熟客、经营较稳定、收摊后有核对空隙、愿意指定替补的店；首批约 **8～15 位自愿熟客**，不一上来招全社区。

先在不忙时约 20～30 分钟沟通，再观察两次真实早高峰。询问：平时哪些熟客几乎天天来？老板本来怎么发现少了人？一天能增加几分钟？休息时谁接手？有无不愿告诉家人的熟客？不要索要老人名单来证明店铺合适。

**与店主沟通话术：**

> 不是让你当监护人，也不是让你保证谁的安全。我们想试试把你本来认识、会打招呼的熟客记清楚一点。熟客自己愿意，联系人也接受；到收摊核对一下，连续几次缺记录再由约定的人问候。先只试少量熟人，不收费、不加设备、不动收款流程；若你感觉多了一份难接住的责任，我们就停。扫码不会的人由你当面帮点。先用纸试一周，看是否真的比原来省心。

不能以“多卖包子”交换店主承担安全责任，也不把“这是公益”作为免责理由。打印、培训、复盘由试点运营方承担；如要补贴工时，事先明确，不按“发现异常人数”奖励。

### 10.2 启动条件

- 用户确认具体店铺渠道，店主本人同意试点；老人本人愿意，守护人本人愿意，不能由子女单方面加入。
- 一位主责、一位授权替补，固定核对时段和歇业办法；不能笼统写“老板或网格员”。
- 实际运营主体、联系渠道、数据期限、退出与投诉办法明确。
- 数据地域、权限、备份和删除能力经验证；没有能力时继续线下，不拿真实信息做未经隔离的演示。
- 老人知道这不替代原有联系照护。不纳入依赖即时异常发现、而现有照护又缺位的人；这不是用年龄一刀切排除。
- 有纸质故障备用办法，限定保管人与销毁时间。

### 10.3 试点节奏

**建议：一周线下验证 + 数字版上线后至少三周观察。** 开发在两者之间，完整日历跨度约 5～7 周，不把“四周试点”说成四周内包含完整开发。

| 时间 | 做什么 |
|---|---|
| 准备 2～3 天 | 找店、访谈/观察、确认主责替补、介绍风险与双方同意 |
| 线下第 1 周 | 纸笔跑核对与私下联系流程，观察漏记与时间负担；无真实资料进原型 |
| 通过线下闸门后 | 按下节排期开发与验证，先用虚构数据 |
| 数字第 1 周 | 店主协助为主，少量老人本人点；每天观察弱网、代点和同意理解 |
| 数字第 2 周 | 稳定流程，正常闭店/请假；用明确标记的演练账号练习未接通与故障 |
| 数字第 3 周 | 更少运营方陪伴，观察店主能否独立持续；访谈老人、店主和守护人，决定停止、调整或继续 |

演练账号不混入真实名单，不偷偷给真实家属发假异常，不故意中断真实服务测试。任何知情撤回立即停止新联系。

### 10.4 观察指标与决策门槛

以下是小样本试点的内部继续/停止标准，**不是安全效果或事故减少的证明**。

| 指标 | 怎么测 | 初步目标/动作 |
|---|---|---|
| 同意理解 | 请老人用自己的话解释“记什么、谁看、没记录怎么办、怎么退出” | 所有参与者都能理解核心边界；未理解先解释，仍不理解不激活 |
| 数据覆盖 | 用授权店主当天观察对照记录；不拍摄、不定位 | 已实际观察到的参与者中正确记录率争取 ≥90%；低于目标先改流程，不扩大 |
| 每日人工闭环 | 当日有无核对者、时间及未结事项 | 试点约定日每天有人核对；漏一次及时补流程，重复缺岗暂停服务 |
| 老板总负担 | 简记常规核对分钟数，电话耗时单独记 | 常规中位数争取 ≤5 分钟/日；持续 >10 分钟或明显影响经营则停止/缩范围 |
| 误报与打扰 | 实际联系后被确认漏记/暂停的次数，分类不记健康细节 | 完整记录分子/分母；真实提醒不足 10 次不作稳定误报率结论。重复流程误报即纠偏 |
| 漏记与漏联系 | 记录错点、名单漏核对、任务未处理、失效联系方式 | 每例复盘；无法连续接住人工流程，不上自动消息掩盖问题 |
| 老人自主性 | 是否觉得被盯、被逼购买或每天交作业，是否自由退出 | 任一投诉认真处理；发现强绑或家属强制则停止该参与关系 |
| 无手机可用性 | 代点占比、老人是否需排额外队 | 代点高不算失败；如果新增等待或反复登记，则调整 |
| 守护人反应 | 是否知道来电人、是否愿意接受、未接通后怎么接手 | 不以“短信发送成功”代替；保持明确的人工未结事项 |
| 真正增量价值 | 店主与家属是否觉得比原来的微信/口头记忆更有帮助 | 若只是把原来工作搬到填表，停止或简化；不因题材有意义继续硬做 |
| 预订需求 | 访谈既有预订习惯与店主微信负担 | 达到真实需求条件再做，不以假问卷“愿意用”代替行为 |

**停止条件：** 无负责人或替补、隐私泄露/公开名单、老人被强制加入、重复无人处理、产品被当成唯一照护、严重影响店铺经营、无法核实数据隔离与位置。停止时向参与者及守护人明确“后续不再由此工具核对/联系”，恢复原有安排并执行删除，不能只把网页关掉。

产品/线下运营、技术/权限、隐私安全三位内部评审均完整阅读 PLAN 与 PRD；发现的问题纳入以下实现约束后，允许直接开发本地假数据原型，不再逐项等待用户选择。未进行真人试点，未证明安全效果。

- 固定一个虚构演示店、预置虚构熟客与联系人、一位模拟店主及授权替补。所有同意、联系方式和联系结果都是模拟，不生成真人同意证据。
- 只允许选择预置角色和有限枚举，不开放自由姓名、电话、住址、健康说明或名单导入；服务端拒绝非演示字段。无电话、tel 链接、剪贴板联系文案、通知和上门入口。
- 前端为移动端 H5 + Vite + TypeScript，全部依赖/测试/构建通过 pnpm，只保留 pnpm-lock.yaml。原型本地后端为 Node TypeScript + SQLite，仅本机持久化；没有开通 MySQL、Qoder Sites 或其他云服务。
- 前后端只绑定 127.0.0.1，优先前端 5217、后端 5218，冲突选择空闲端口，不终止其他进程。不部署、付费、申请公众号、联系真实店铺/守护人、提交 git 或改全局配置。
- PRD 的“今天挺好”、四位数身份访问、家属轨迹看板、没来敲门等旧设想不进入本原型；前文真实试点与云资源闸门只约束未来真实运营。

### 14.2 产品与线下运营评审

一张名单不是安全服务。5 分钟只是日常核对目标，不能遗漏代点、补记、接班和联系耗时。按 15 人示例，代点每人 10～20 秒约 2.5～5 分钟，核对/补记约 3～5 分钟，常规总额可能 6～10 分钟；每次联系另约 3～10 分钟，未接通/交接日可能额外 10～30 分钟。这是演练预算，尚无真实店主工时证据。

- 本地提供模拟营业日期、逐日开/闭店、每日核对和替补处理；全店暂停核对联系是明确状态，不伪造已接班。
- 联系事项先领取，记录负责人；未接通必须保持跟进并选择下次处理日期，只有明确模拟接手才结案，接通不等于安全。转交需目标替补主动领取；无人接手时暂停模拟服务。
- 不实现无上限自动重试：至多三次手工假联系尝试，仍未接通时只允许暂停该模拟联系约定，重新接受后另开新周期。实际频次、截止及应急分工待真人运营审批。

### 14.3 日期、核对和事项规则

| 日期状态 | 连续缺记录计算 | 可进入联系事项吗 |
|---|---|---|
| 已记录 | 连续数归零 | 否；已有未联系事项撤销 |
| 已登记请假 | 连续数归零 | 否 |
| 明确闭店、非约定到店日 | 跳过，不累加 | 否 |
| 尚未核对或数据/核对版本失效 | 未知，打断可靠连续推断 | 否；仅“补核资料” |
| 已核对、营业且约定到店、无记录 | 连续数加一 | 达 1/2/3 个自选阈值后先人工核实 |

报名后从下一个约定营业日开始，不追溯计缺席。未知前后的日期不连计；未知之后已经形成达到阈值的连续已核对缺记录，可建立新的有效依据，不强求补齐更早未知历史。原型只在报名时选择阈值与通常到店日，暂不开放追溯改规则。每日核对绑定当天名单版本；记录撤销、报名/同意状态变化、请假新增/撤回、开闭店修改均使受影响日期需要重新核对。晚到直接取消不再成立的未联系事项；已经假联系的事项保留更正待办，由授权人员手工标记已更正。每次领取和记录结果前重算依据，不以旧页面或发送行为证明安全。

### 14.4 技术/权限与隐私评审

- 公共 API 只返回虚构店铺介绍及声明，不返回任何名单或角色凭证。店主和替补用本机受控模拟账号口令登录，口令不打包进前端；登录会话为高熵 HttpOnly Cookie，写入校验 Origin、CSRF 和对象权限。
- 店主/替补仅管理本演示店；本人仅查看自己并提交自己当天记录/请假/退出；守护人仅模拟接受/撤回自己的联系约定，不查看轨迹、不代点、不改老人资料。
- 由店员签发短时单次高熵配对票据，仅在受控操作中交换身份，不进入 URL、浏览器持久化或公开店码。现场代点按单人确认，不提供“全员到店”按钮。
- 单进程 SQLite 事务内更新业务状态、去重与事项；记录按店/人/日期唯一。同幂等键不同请求拒绝；本人/代点重复收敛并保留首个来源。核对、请假、事项操作用版本校验。
- 退出/撤回立刻撤销关联设备权限、停止事项；原型立即删除关联假记录、请假、联系人模拟状态、票据和事项，重启不会恢复。保留的只有不含称呼、电话或内容的必要操作标识；没有真实法定归档证据，也没有云备份。
- 本地持久化目录不在静态目录内，不提交或对外提供；不使用 localStorage/sessionStorage 保存资料、口令或凭证；响应不缓存，服务器不记录请求正文、Cookie 或秘密。提供仅店主可用的“清空演示数据”，重新生成假夹具并撤销旧会话。

### 14.5 验收与真实运营待办

必须通过 pnpm 类型检查、构建和规则/权限测试，再实际浏览器手机尺寸操作：模拟登记及双方接受 → 本人记录/店员代点 → 请假/店休/未知 → 每日核对 → 缺记录事项 → 领取并记录假联系结果 → 晚到更正 → 退出删除和越权拒绝。仅使用本任务自己的浏览器页，不关闭或覆盖他人页面。

真实试点仍需另批：具体店铺、具名运营主体与替补、真人双方同意、实际工时/联系频次、法律与影响评估、数据地域/服务链、保留删除/备份/故障应急、公网与云费用。所有这些保持待办，不能由本地测试通过推导已获授权或安全已保障。

### 14.6 实现后只读复核与修复

另一次内部代码复核完整检查后端、前端及测试，提出四个具体缺陷，均已修复并加入回归：联系人撤回同步清理假到店/请假/含内容回执；联系结果先校验字符串类型，数组/对象不能绕过未接通日期规则结案；同一连续段因闭店更正只更新原事项及更正待办，不重复创建联系事项；核对列表显示完整已模拟日期，七天以前的未知也可补核。另补充重复模拟接受不重置起算或清除事项，以及未知之后达到阈值的已核对新连续段不被更早未知错误冻结。

更正事项保留原依据日期，必须授权人员手工标记假更正，不能因再次重算而自动结案。两个手机用例均独立重置自己的假夹具，不依赖前一个测试留下的登记。浏览器断网提示改为中文“资料状态未知”，不以空名单掩盖读取失败。

### 15.4 写入结果与读取失败的反馈分离（2026-11-17，待主会话复验）

主会话复验发现一处遗漏：`perform` 把写入与随后的重新读取放在同一个 catch 里，导致 review 已 200 落库、但首次 GET /api/staff 返回 500 时，页面仍提示“本次操作没有保存”。本次只局部修正 `src/main.ts` 的 `perform`，没有改服务端权限和 SQLite 业务规则，也没有引入通用框架：

- 写入返回 4xx（服务端明确拒绝）：提示“本次操作没有保存”，再尝试重新读取。
- 写入返回 5xx：结果未知，因为服务端可能已经提交。
- 网络在收到响应前断开：结果未知、“不一定完成”，不自动重发 POST。
- 写入已确认、但随后读取 500 或断线：提示“后端已确认：…但随后读取最新资料失败…无需重复提交”。页面进入“资料状态未知”，“重新读取资料”按钮在最前，不显示任何核对、联系、代点等按钮。
- “重新读取资料”只发 GET：
  - 仍失败时保留“此前后端已确认：…”；
  - 恢复后提示“已从本地后端重新读取最新资料。此前后端已确认：…请以下方最新状态为准”，并以最新读取的状态为准。
- 核对、本人到店、代点、请假、假联系结果、登记、同意都走同一个 `perform`，同样适用以上规则。

新增隔离浏览器回归（tests/browser.spec.ts 第 4–6 个用例）：

1. 真实 review 返回 200 后，首次读取 500：
   - 服务端确实已核对，反馈不含“没有保存”；
   - 重读后显示“今日已核对”；
   - 全程只有 1 次 POST /api/review。
2. 320 宽、28px 大字下，代点写入成功后读取持续失败：
   - 两次重试仍未知，重试按钮底边在首屏内；
   - 没有可操作按钮、没有新的 POST；
   - 恢复后只重读，显示“今天已记录”，arrival POST 只有 1 次。
3. 写入前断线和明确拒绝：
   - review 请求被中止：提示“不一定完成”，服务端未核对，不重发；
   - 版本冲突 409：提示“本次操作没有保存”，不报成功。

原有权限、大字布局用例保持通过。截图在 `artifacts/after/`：`committed-then-read-500-390.png`、`committed-read-fail-320-large.png`、`committed-read-recovered-320-large.png`。
