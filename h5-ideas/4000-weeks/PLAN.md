## 1. 待定问题逐条回答

### 1.1 一格 = 从生日起每 7 天，还是对齐自然周？——推荐自然周 【待确认】

**两种方案对比**

| | A. 生日起每 7 天 | B. 自然周（周一 ~ 周日） |
|---|---|---|
| 单人图 | 第 1 格正好是出生那 7 天，最「纯粹」 | 第 1 格是出生所在的那个自然周（可能只有 1~7 天） |
| 两人对齐 | 两人的格子错开 0~6 天，**同一格对应不了同一段日子**；只能按「部分重叠」去算，图上画不齐 | 同一周就是同一周，**同一列 = 同一周**，直接对齐 |
| 「本周记录」 | 每个人的「这周」起止日都不一样（我的这周是周三到周二，孩子的是周六到周五），没法一次给全家写 | 全家共用同一个「这一周」，周日晚上一次写完 |
| 「一起的周」 | 认识那天落在两人各自格子的不同位置，重叠区边界含糊 | 认识那周就是一个确定的格子，两人图上都在同一周 |
| 跨人自动标记 | 难：孩子出生那周落在我的哪一格要换算 | 自然：孩子出生那周在我的图上自动出现「小满出生」 |
| 每周提醒 | 每人提醒日不同 | 统一周日晚 |
| 代价 | — | 第 1 格可能不满 7 天；「第 N 周」和严格按 7 天算的结果最多差 1 |

**结论**：多人对齐是这个产品的灵魂，而 A 方案下「同一格」在不同人之间根本不是同一段日子，对齐视图、共写、「一起的周」都会变得别扭甚至做不成。B 的代价（第一格不满 7 天）用户几乎感知不到。**推荐 B：自然周、周一开始（ISO 8601），全局统一的周编号。**

**单人格子图怎么分行（B 方案的配套设计）**

- 每一行 = 一个「岁」：从第 n 个生日所在的那周开始，到第 n+1 个生日所在那周之前结束。
- 所以**生日那周永远是每行的第一格**，左侧刻度「0、10、20…岁」是准的，不会像 Tim Urban 原图那样每年漂 1.24 天、80 岁时漂出 3 个多月。
- 代价：一行有 52 或 53 格（大约每 5~6 年出现一次 53 格的年份），右边缘偶尔多出一格。画布按 53 列排版，多出的那一格反而像「这一年多了一周」，可以接受。**【待确认】你是否接受「一行 52 或 53 格」**；如果坚持严格 52 格一行，就要接受刻度逐年漂移。

**对齐视图怎么分行**

- 每一行 = 一个公历年（ISO 周年，按「周四落在哪一年」归属，52 或 53 列），年内按人分成几条细行（泳道）。
- 不同人同一列就是同一周，上下对齐一眼可见。

**周的起始日**：固定周一，不做成可配置（改起始日会让所有记录换格子）。

### 1.2 MVP 是否就带对比视图？——推荐带精简版 【待确认】

- 你特别强调多人对齐是核心亮点；如果 MVP 不带，这个产品看起来就是「又一个 Life in Weeks」，差异化出不来。
- 由于 1.1 选了自然周，对齐视图的数据层几乎是零成本，主要成本是一个新的渲染布局，估约 2 天。
- **精简范围**：
  - 选 2~4 个人；
  - 只画到今年为止（不画未来，避开「谁先走」的联想）；
  - 高亮「一起的周」（伴侣从相识那周起，其他人从两人都在世的那周起）；
  - 顶部两三句总结：「你和阿洋一起走过 412 周」「小满来到你们身边 87 周」。
- **不进 MVP**：以「我」的格子为底叠加其他人的模式、导出对齐长图。
- 另外，即使不打开对齐视图，单人图上也会**自动出现跨人标记**：我的图上有「小满出生」「认识阿洋」，父母的图上有「你出生了」。这一项几乎零成本，放进 MVP。

备选：先做「单人格子图 + 陪伴计算器」，对齐视图放到第二版，排期能少约 2 天。

### 1.3 是否支持照片？——MVP 不带，第二版做 【待确认】

理由：
1. **备份变复杂**：现在一个 JSON 就能完整备份；加了照片要改成 zip，导入/合并逻辑也会翻倍。
2. **iOS 的存储风险**：Safari 对「没添加到主屏幕」的网站，7 天不访问可能清掉本地数据。纯文字丢了还能从 JSON 恢复，照片体积大、用户更不愿意频繁备份，丢失的伤害更大。
3. 「一周一句」的克制正是它的气质；照片很容易让它变成另一个相册。

第二版方案（先记下来）：每周最多 1 张；长边压缩到 1080px，转 JPEG/WebP，质量 0.8（约 100~200KB）；单独放一个 `photos` 表存 Blob；备份改为 `.zip`（JSON + 图片）；调用 `navigator.storage.estimate()` 显示占用。

### 2.1 技术栈

| 层 | 选择 | 理由 |
|---|---|---|
| 构建 | Vite + TypeScript（strict） | PRD 已定 |

### 2.2 约 4,700 个格子的渲染

**为什么用 Canvas 不用 SVG**：4,700 个 `<rect>` 能画，但双指缩放时每帧都要重排 DOM、本周格子的呼吸动画也会触发整棵树重绘，低端安卓上会掉帧；而且第二版的海报导出本来就要用 Canvas。用 Canvas 的话，一次 `fillRect` 画完 4,700 格不到 1ms。

**布局（单人图）**
- 53 列 × N 行，N = max(画到多少岁, 当前年龄 + 1)。
- 手机宽 375px：左侧刻度留 24px，右边距 12px，每格占约 6.3px（格子 5px + 间隙 1.3px）；90 行高约 570px——**一屏装下一整个人生**，这就是第一眼的冲击力。
- 预先算出每一行的起始周编号和格数（52/53），之后渲染和点击命中都查这张表。

**绘制**
- 画布 CSS 尺寸 = 视口大小，像素尺寸 × devicePixelRatio（上限 3）。
- 两层：
  1. **静态层**：所有格子，按填充色分组批量 `fillRect`，减少 `fillStyle` 切换；只在数据变化或缩放/平移时重画（rAF 节流），只画可见区域。
  2. **动效层**：一个叠在上面的小 canvas，只画本周那一格的呼吸效果。页面隐藏（`visibilitychange`）时停掉；系统开启「减少动态效果」（`prefers-reduced-motion`）时改成静态描边。
- 缩放到每格 ≥ 18px 时，在格内画 emoji；≥ 40px 时显示日期小字。

**缩放与平移**
- 自己维护变换 `{scale, tx, ty}`，范围 1× ~ 8×；用 Pointer Events 处理单指拖动、双指捏合；双击在 1× 和 4× 之间切换（以点击处为中心）；滚轮/触控板也支持缩放。
- 加 `touch-action: none` 防止浏览器整页缩放。1× 时不允许平移，避免误触。

**点击命中**
- 屏幕坐标 → 用逆变换得到画布坐标 → `row = floor((y - top) / pitch)`、`col = floor((x - left) / pitch)` → 查行表得到周编号，越界就忽略。间隙算进最近的格子，提高容错。
- **1× 下一格只有 5px，手指点不准**：点击时选中最近的一格并加一个高亮圈，底部弹层里提供「‹ 上一周 / 下一周 ›」微调。这比强制先放大更顺手。
- 无障碍：canvas 设置 `role="img"` 和概括性的 `aria-label`（如「小满的格子图，已陪伴 87 周，写过 40 周」）；底部弹层和本周记录页都是普通 DOM，可以被读屏读到。

**对齐视图**
- 按年分组，每组 = 选中人数条细行（每格 6px）。4 个人、跨度 100 年时总高约 3,900px。
- **不能画成一张超长 canvas**：iOS 对 canvas 面积有上限（约 1,670 万像素），乘以 3 倍像素比会超。做法：外层是原生滚动容器 + 一个撑出高度的占位 div，canvas 用 `position: sticky` 固定为视口大小，滚动时只重画可见的年份（虚拟滚动）。右侧加一个年份快速定位条。

### 2.3 IndexedDB 数据模型

数据库名 `four-thousand-weeks`，版本 1。

```ts
type Relation = 'self' | 'child' | 'partner' | 'parent' | 'pet' | 'other'

type Life = {
  id: string                 // crypto.randomUUID()
  name: string
  relation: Relation         // 相对「我」的关系；self 最多一个
  birthDate: string          // 'YYYY-MM-DD'，公历日，不带时区
  endDate?: string           // 「TA 已经离开了」（可选）
  drawToAge: number          // 「格子画到多少岁」，默认：自己 90、父母 90、宠物 15
  showFuture: boolean        // 默认：只有 self 为 true；child 强制 false 且不可改
  color: ThemeKey            // 色板里的键，不存十六进制，方便以后换主题
  metDate?: string           // 伴侣：相识那天
  meetPerYear?: number       // 父母：一年见几次
  daysPerMeet?: number       // 父母：每次待几天
  livesTogether?: boolean    // 父母：住在一起（这时不算次数）
  phone?: string             // 父母：可选，只用来生成「打个电话」按钮
  order: number
  createdAt: number
  updatedAt: number
}

type WeekEntry = {
  lifeId: string
  week: string               // 那一周的周一，'YYYY-MM-DD'（全局统一的周键）
  text?: string              // 一句话，建议不超过 60 字（有字数提示，不强制截断）
  color?: MoodKey            // 不填就用这个人的主题色
  emoji?: string             // 单个字形（用 Intl.Segmenter 校验）
  milestone?: string         // 里程碑标题，如「会走路」
  met?: boolean              // 父母：这周见到了
  updatedAt: number
}
// 主键 [lifeId, week]；索引 week（对齐视图、「本周全家」用）、lifeId

type Settings = {            // 键值表
  schemaVersion: 1
  leftHomeAge: number        // 你几岁离开家，默认 18（陪伴计算器用）
  lastBackupAt?: number
  theme: 'auto' | 'light' | 'dark'
  onboarded: boolean
}
```

**与 PRD 草稿的差异**：
- `weekIndex`（从出生算第几周）改成 `week`（那周周一的日期）。这样同一周在所有人之间是同一个键，导出的 JSON 人也看得懂；改了生日后记录仍然停在原来那一周，不会整体错位。「第 N 周」在显示时现算。
- 里程碑里有一部分是**推导出来的、不存库**：出生那周、相识那周、孩子出生在「我」图上的那一格、我出生在父母图上的那一格。改日期时它们自动跟着变，不会出现不一致。
- 改生日后，如果有记录落在新生日之前：保留这些记录，并提示「有 N 条记录在出生之前」，由用户决定是否删除。

**数据量**：一个人写满 90 年，约 4,700 条 × 约 100B ≈ 0.5MB，可以忽略不计。

### 2.4 日期计算（重点，全部写单元测试）

- **只用「公历日」，不用时刻**：日期存为 `'YYYY-MM-DD'` 字符串；计算时转成整数「日序号」`day = Date.UTC(y, m-1, d) / 86400000`。全程在 UTC 下做整数运算，**不会受夏令时和时区影响**。
- **今天** = 设备本地时区的年月日（`getFullYear/getMonth/getDate`）。用户出差跨时区，最多让「本周」的切换早或晚几小时，可以接受。
- **周编号**：1970-01-01 是周四。`weekId = Math.floor((day + 3) / 7)`，这一周周一的日序号是 `weekId * 7 - 3`。
  - ⚠️ 父母大多出生在 1970 年之前，日序号是负数，**必须用 `Math.floor`**，不能用 `|0`、`~~` 或 `%`（对负数结果不对）。
- **闰年**：交给 `Date.UTC`，不自己判断。
- **2 月 29 日出生的人**：平年的「生日」按 2 月 28 日算（写进代码注释和测试）。
- **单人图第 n 行**的起点 = 第 n 个生日（出生年 + n）所在周的 weekId；行长 = 下一行起点 − 本行起点 ∈ {52, 53}。
- **第 N 周** = 本周 weekId − 出生那周 weekId + 1；伴侣的「一起的第 N 周」从相识那周开始算。
- **对齐视图的年份归属**：ISO 周年，即这一周的周四落在哪一年。
- 需要覆盖的测试：1970 年前出生、2 月 29 日出生、出生在周日或周一、跨年那一周、生日恰好是周一、有 53 周的年份、今天就是生日。

### 2.5 导出与导入

- **导出**：
  ```json
  { "app": "one-week-one-cell", "schemaVersion": 1, "exportedAt": "…",
    "lives": [...], "entries": [...], "settings": {...} }
  ```
  文件名：`一周一格-备份-2026-11-17.json`。
  - 支持 `navigator.share({ files })`（iOS/安卓的分享面板，可以存到文件或发给自己）时优先用它；否则用 Blob 下载。
  - 微信内置浏览器两条路都不通：提示「点右上角，在浏览器中打开」。
- **导入**：选文件 → 校验（手写一个轻量校验器：检查 `app` 字段和版本号，逐字段做类型检查，丢弃未知字段）→ 预览「将导入 4 个人、523 条记录」→ 二选一：
  - **合并（默认）**：人按 id 匹配，记录按 `[lifeId, week]` 匹配，`updatedAt` 新的那条保留；
  - **覆盖**：二次确认后清空再导入。
- **防丢数据**：
  - 首次写入后调用 `navigator.storage.persist()`，申请持久化存储；
  - 距上次备份超过 30 天且期间有新记录时，首页顶部出一条轻提示「已经一个月没备份了」（可关闭）；
  - 引导 iOS 用户「添加到主屏幕」（加到主屏幕的网页应用不受 Safari 7 天清理规则影响）。
- **安全**：所有用户文本只用文本方式渲染（Preact 默认转义），不使用 `innerHTML`；导入时限制文件大小（如 20MB）。

### 2.6 PWA

- manifest：名称、`display: standalone`、主题色（暖白）、图标（192/512，加 maskable 版本），另配 `apple-touch-icon`。
- Service Worker：预缓存全部静态资源，可以完全离线使用；新版本出来时提示「有新版本，点此刷新」，不自动刷新，避免用户正在输入时被打断。
- iOS 没有安装弹窗：在 Safari 里第 2 次打开时，显示一次图文引导「分享 → 添加到主屏幕」。
- **每周提醒（第二版）**：纯前端没办法可靠地定时推送（Notification Triggers 已经被放弃，Web Push 需要服务器）。纯前端的替代方案：生成 `.ics` 日历订阅（每周日 20:00，`RRULE:FREQ=WEEKLY;BYDAY=SU`），导入系统日历后由日历负责提醒。
- 部署：任意 HTTPS 静态托管即可（PWA 要求 HTTPS）。

### 3.5 父母陪伴计算器

```
┌────────────────────────────────┐
│ ←  妈妈                         │
│    妈妈今年 67 岁                  │
│                                │
│ 一年大概回去几次？      [ − 2 + ]   │
│ 每次待几天？           [ − 5 + ]   │
│ □ 我们住在一起                     │
│                                │
│       按这样算，                   │
│       你们还能再见  约 46 次         │
│       一起待  约 230 天            │
│                                │
│  ○○○○○○○○○○○○○○○○○○○○○○○○   │ ← 一个点 = 一次见面
│  ○○○○○○○○○○○○○○○○○○○○○○      │   今年已见的那几个是实心的
│                                │
│  如果每年多回去 2 次，就是约 92 次。    │ ← 给出可以行动的方向
│                                │
│  从你出生到 18 岁离家，               │
│  你们朝夕相处了约 6,500 天。          │ ← 已经拥有的，不是「用掉了 90%」
│                                │
│  [ 打个电话 ]   [ 这周见到了 ]        │
│                                │
│  按 90 岁粗略估算，只是一个提醒。可调   │ ← 小字
└────────────────────────────────┘
```

- **算法**：剩余年数 = 画到的岁数 − 当前精确年龄；次数 = 向下取整(剩余年数 × 每年次数)；天数 = 次数 × 每次天数。都带「约」字。
- **不出现**「剩余 XX 周」「还剩」「寿命」「%」这些词；见第 3.6 节的词表。
- **边界情况**：
  - 当前年龄 ≥ 画到的岁数：不显示数字，只写「每一次见面都很珍贵」，再加「打个电话」按钮；
  - 勾选「住在一起」：不算次数，写「能每天见到，多一起吃几顿晚饭」；
  - 父母已离开：没有计算器，只显示「一起走过 N 周」和那张格子图。
- **「打个电话」**：存了电话就是 `tel:` 拨号链接；没存时，第一次点击引导填一下（只存在本地），也可以跳过（直接拉起拨号盘）。
- 拖动「一年几次」的加减器时，点阵实时增减，加号带一个轻微的「多出来」动效——让人想按加号，而不是被数字吓到。

### 3.6 措辞词表（写进 `copy.ts`，每次改文案都对照）

| 不用 | 改用 |
|---|---|
| 剩余 / 还剩 XX 周 | 还能再见约 N 次（父母）、未来（只在自己的图上，且只用留白表示，不写字） |
| 已活 X% / 已用掉 | 第 N 周、已记下 M 周、已陪伴 N 周 |
| 预期寿命 | 格子画到多少岁 |
| 倒计时、死亡、寿命用完 | 不出现 |
| 你还没写！（催促） | 这一周还空着，写一句？ |
| 删除这个人 | 移除（并二次确认：「TA 的 312 条记录也会一起移除」） |

## 4. 视觉方向

**整体**：像一本摊开的手账。暖白纸色、大量留白，格子是唯一的主角；不用红色，不用大号的数字冲击。

**配色**

| 用途 | 浅色模式 | 深色模式 |
|---|---|---|
| 背景（纸） | `#F7F3EC` | `#1C1A17` |
| 主文字（墨） | `#2B2A28` | `#EDE7DC` |
| 次文字 | `#8A8378` | `#9A9286` |
| 未来格子（留白） | 1px 描边 `#DDD5C8`，不填色 | 描边 `#3A362F` |
| 走过但没写 | `#D3CABC` | `#4A453D` |
| 一起的周（底色） | `#F3E3D6` | `#3B2F28` |
| 里程碑 | 金色 `#C9A227` | `#D9B64A` |

**人物主题色**（低饱和，8 个）：赤陶 `#C46A4A`（自己默认）、玫瑰 `#C97B84`（伴侣默认）、向日葵 `#D9A441`（孩子默认）、鼠尾草 `#7E9C82`（父母默认）、雾蓝 `#6F8FAF`、梅 `#8E6C8A`、湖绿 `#4F9A94`（宠物默认）、石板 `#6B7280`。

**格子状态的区分**（1× 时每格只有约 5px，只能靠颜色和明度区分）

| 状态 | 画法 |
|---|---|
| 未来 | 只描边、不填色——「留白」 |
| 走过、没写 | 浅暖灰实心 |
| 写过 | 心情色或人物主题色实心，饱和度明显更高 |
| 里程碑 | 写过的颜色 + 外圈 1px 金色描边；格子图左侧对应行旁边加一个小金点，在 1× 下也能找到 |
| 本周 | 主题色描边 + 呼吸光晕 |
| 被选中 | 墨色 2px 圆角描边 |
| 一起的周（伴侣） | 格子背后铺一层暖色底 |

放大到每格 ≥ 18px 时显示 emoji；≥ 40px 时显示日期，格子圆角也随着放大变大一些，看起来像一张张小卡片。

**字体**：系统无衬线（PingFang SC），数字用等宽数字（`font-variant-numeric: tabular-nums`）；**那一句话用衬线体**（Songti SC / Noto Serif SC，安卓没有就回退到系统 serif），读起来像手写的日记。

**动效**（全部遵守 `prefers-reduced-motion`）
- **本周呼吸**：2.4 秒一个循环，ease-in-out；外圈光晕透明度在 0.15 ↔ 0.55 之间、半径 0 ↔ 2px 之间变化，像心跳一样慢，不是闪烁报警。减少动态时改为静态双描边。
- **写完一句**：格子从中心「墨水晕开」——填充色从 40% 的面积扩散到 100%，300ms，再带一个很轻的回弹；一次性的小奖励。
- **首次打开**：格子按行从上到下依次亮起，约 1.2 秒，每次会话只播一次。
- **对齐视图**：切换选人时，细行滑入或滑出（200ms）。

## 6. 需要你拍板的决定（汇总）

1. **周的定义**：自然周（周一开始）+ 每行从生日那周开始、一行 52/53 格（推荐）／生日起每 7 天、严格 52 格一行
2. **MVP 是否带对齐视图**：带精简版，约 12.5 天（推荐）／不带，约 10.5 天
3. **照片**：第二版再做（推荐）／MVP 就做
4. **产品名**：一周一格（推荐）／4000 周／人生格子／一生

### 7.2 日期算法（这是对齐能否成立的根本）

| # | 检查点 | 结论 / 实现约束 |
|---|---|---|
| D1 | 周编号的公式 | `day = Date.UTC(y, m-1, d) / 864e5`，`weekId = Math.floor((day + 3) / 7)`，这周周一 = `weekId * 7 - 3`，周四 = `weekId * 7`。1970 年前出生时日序号是负数，必须用 `Math.floor`；单元测试覆盖 1950 年代的日期。 |
| D2 | 单人图每一行能否稳定是 52 或 53 格 | 第 n 行的起点 = 第 n 个生日所在周。相邻两个生日相隔 365 或 366 天，跨过的周一个数只能是 52 或 53。单元测试遍历多个生日、每人 100 行：校验每行长度 ∈ {52, 53}、行与行首尾相接、总格数等于出生周到最后一周的周数。 |
| D3 | 2 月 29 日出生 | 平年的生日按 2 月 28 日算，这样 2/28 → 次年 2/29 之间的间隔仍是 365/366 天，D2 的结论依然成立。有测试。 |
| D4 | **对齐必须是真正按日历对齐，不能是「把两张生日图并排放」** | **对齐视图不复用单人图的行布局**。它的行 = ISO 周年，列 = `weekId - 该年第一周的 weekId`，每人只是在这一行里画自己存活的那一段。所以「同一周 = 同一个 weekId = 同一列」是由构造保证的。单元测试：生日不同的两个人，在同一个日期上的列号必须相等。 |
| D5 | 跨年那一周 | 按 ISO 规则，这一周周四在哪一年就归哪一年。比如 2024-12-30 那一周（周一）会出现在 2025 年那一行的第 1 列；弹层里显示精确的起止日期，避免误解。有测试：2020 年有 53 周、2021 年有 52 周、2026 年有 53 周、2024-12-30 那周属于 2025 年。 |
| D6 | 出生在周日 / 周一 | 周日出生：出生周的周一在 6 天前，第 1 格只有 1 天。周一出生：第 1 格满 7 天。两种都有测试。 |
| D7 | 「今天」和跨午夜 | 「今天」取本地日期；页面重新可见时，以及每分钟检查一次，跨过周日 24 点时「本周」自动切换。 |
| D8 | 输入校验 | 拒绝：格式不对、不存在的日期（如 2023-02-29）、早于 1900 年、**晚于今天**的生日；离开的日子必须在生日到今天之间；相识日不能早于生日、不能晚于今天。 |
| D9 | 设定的岁数小于当前年龄 | 行数 = max(设定的岁数, 当前年龄 + 1)，保证本周一定画得出来。 |

### 7.3 数据安全与可用性

|---|---|---|
| S1 | 删除一个人会不会误伤别人 | 在同一个 IndexedDB 事务里，只按 `lifeId` 索引删这个人和这个人的记录；确认弹窗写明「TA 的 N 条记录也会一起移除」。用 fake-indexeddb 写测试：删掉 A 之后，B 的人物和记录完全不变。 |

## 9. 验收返修与自测（2026-11-17，待独立复验）

### 9.1 数据安全和日期边界

- **P0 过期导入预览**：预览同时保存当时实际持久化的 Dataset。提交在包含人物、周记录、快照的同一个 IndexedDB readwrite 事务中重新读库、分析冲突并比较完整数据签名。人物/记录的新增、修改、删除以及时间戳/排序变化都使原预览失效：不写存档、不建/裁剪快照，更新预览、恢复默认保本机，要求用户再次确认。完全替换的二次确认也走同一检查，不绕过。
- 确认的基线仍有效时，在该事务内保存准确的导入前快照，再合并/替换，最后等待事务提交。恢复快照也把「恢复前快照 + 替换」放在一个事务；异常会回滚存档、快照创建及裁剪。`mergeDatasets` 对 added 人物/周键另作存在性保护，旧 added 不会覆盖后来存在的同键，即使误用旧计划也如此。未停掉 BroadcastChannel，没有把导入问题混同于普通同周编辑最后保存优先。
- 补查替换后的排队保存：写周记录在人物+记录事务里确认人物仍存在。替换/恢复已移除的人物若收到旧页面排队保存，会拒绝写入，而非留下无人物的孤立记录；仍存在人物的后排队记录正常保留。
- **P1 高龄生日自然周**：`rowCountFor` 在实际年龄/设置的行数下界之外，继续检查下一生日所处的周是否已经到达当前或离开周。精确例 `1930-11-20 → 2026-11-17, drawToAge=90` 现在为 97 行，实际年龄仍为 95，当前周 `2026-11-16` 可定位。关闭未来时末格就是该周；开启未来时该行剩余周仍按原未来策略绘制。没有抬高陪伴假设年龄，也不泛称所有 90 岁以上人物都会缺格。

### 10.2 区分提交失败与提交后故障

- `afterWrite` 只在存档写入 API 等待事务成功后执行。元数据、BroadcastChannel 通知、真实存档重读分别尝试：某一环节失败不会跳过其余环节，也不把已经提交的数据伪装成回滚。
- `reload` 先发布人物/周记录，再独立读取保存时间等元数据；元数据读取失败不会丢弃已经读到的新存档。存档重读失败立即再读一次，不重放导入/恢复/保存，不额外创建快照。
- 元数据失败反馈「数据已写入本机，无需重复保存、导入或恢复。保存时间或存储授权信息未更新」；单次重读失败恢复后说明「现已重新读取本机存档」；两次读取都失败说明页面尚未读到最新存档；通知失败单独说明其他标签页需重读。不是吞掉故障或笼统宣称成功。
- 共享警告条沿用已有卡片样式，跨路由保留，提供只读的「重新读取本机数据」。成功重读清除警告；持续失败保留明确核对提示。正常路径不新增视觉元素。
- 导入已提交时关闭旧预览、展示实际合并结果；恢复、人物新建/编辑/删除、陪伴设置和单周记录同样保留已提交语义。本周自动保存只在真实写入失败时显示「没保存上」，提交后辅助故障仍显示已保存与共享警告。
- 真正存档事务 abort 仍拒绝；导入/恢复原有「本机数据没有改变」只用于提交失败，原生数据库与快照确实未变。没有承诺提交后回滚，也没有通过重试存档操作消除同步警告。

实现路径：`src/state/store.ts:44`、`:53`（存档与元数据分开）、`:68`（只读恢复）、`:90`（跨页重读）、`:123`（提交后阶段反馈）、`:226`（导入）、`:237`（恢复）；`src/App.tsx:31`（共享警告和重读按钮）；`src/pages/PersonForm.tsx`、`src/pages/LifePage.tsx`、`src/ui/ui.tsx`（保存反馈）。本轮未修改 `BackupPage` 的正常设计，事务 API 的拒绝边界使原有失败分支不再接收上述提交后故障。
